# 29-D4. 위임 실행: 경로와 대체

상태: **Proposed**. 현재 제품 동작을 설명하지 않는다. · 기준일: 2026-11-21 · 기준 커밋: `33a12b72` (`origin/prerelease`) ·
상위: [plan 29 위임 실행](29-akra-delegated-execution.md) (§7) · 선행: [D1](29-d1-contract-and-ledger.md)

## 목표

기능마다 백엔드의 우선순위를 정한다. 백엔드에 토큰이 없거나 서비스가 비정상이면 다음 백엔드로 넘어간다. 넘어가는
규칙은 끝 원인과 부작용 등급이 정한다.

## 지금

- 경로가 없다. 소비자마다 구현 하나가 조립된다 (`composition/production.rs`).
- 백엔드의 건강을 읽는 곳이 없다. 사용 한도는 턴이 실패한 뒤에만 안다 (`UsageLimitExceeded`).
- 정책 파일의 방식은 있다: `issue-policy.toml`, plan 28 §7.3 의 사용자 파일과 저장소 파일.

## 계약

- 정책의 모양은 plan 29 §7.1 이다. 이 조각이 키 이름을 확정한다.
- 값마다 저장소 > 사용자 > 내장 순서로 정한다. 예외: 백엔드의 허락, `tool_access`, 예산의 최대값은 사용자 파일에서만
  온다. 저장소 파일은 줄일 수만 있다.
- 깨진 파일은 `policy_blocked` 이다. 그 기능의 새 작업을 받지 않는다. 내장 값으로 돌지 않는다.
- 작업은 접수할 때의 정책 판(내용의 SHA-256)을 적는다. 경로는 접수할 때 고정한다. 정책이 바뀌어도 진행 중인 작업의
  경로는 바뀌지 않는다.
- 대체의 규칙은 plan 29 §6.2 의 끝 원인 표와 §7.3 의 등급 표이다.
- 회로는 백엔드마다 하나이다. 저장소의 장부에 둔다. `chatgpt_chat` 의 한도는 머신 전체의 값이고 tunnel frontend 의
  `status` 가 알린다. kernel 은 그 값으로 회로를 닫는다. `quota` 는 `retry_at` 까지, `transient` 는 연속 실패 뒤 정한 시간 동안
  닫는다. 닫힌 백엔드는 고르지 않는다.
- 대체할 때마다 `delegation_fell_back` 을 기록한다: 앞의 백엔드, 끝 원인, 다음 백엔드.
- 경로를 다 쓰면 작업은 `failed` (`route_exhausted`) 이다. 화면은 백엔드마다 실패한 이유를 보인다.
- 예산을 넘으면 접수를 거절한다 (`budget_exhausted`). 조용히 쌓지 않는다.

## 완료 기준

- [ ] 첫 백엔드가 `unavailable` 이면 보내기 없이 둘째 백엔드로 간다.
- [ ] `quota` 뒤 `retry_at` 전에는 그 백엔드를 고르지 않는다. 재시작 뒤에도 같다.
- [ ] `read_only` 작업은 전달 뒤 `interrupted` 에서 백엔드의 복구가 `exhausted` 가 된 뒤에 다음 백엔드로 간다.
- [ ] `side_effecting` 작업은 전달 뒤에 자동 대체가 0회이다. 주의 항목이 열린다.
- [ ] 전달이 `uncertain` 인 동안 대체가 0회이다.
- [ ] 저장소 파일이 사용자 파일에 없는 백엔드를 켜지 못한다. `tool_access` 를 올리지 못한다.
- [ ] 같은 입력은 같은 선택이다 (순수 함수의 표 기반 시험).

## 검증

- `command`: 표 기반 단위 시험, 시뮬레이션 시험 (가짜 백엔드 둘, 가짜 시계).
- `data`: 사건 기록의 `delegation_fell_back`, 장부의 회로 상태.

## 제외

- 비용이나 품질로 백엔드를 고르는 것. 여러 백엔드에 동시에 보내는 것. 작업 중의 경로 변경.
