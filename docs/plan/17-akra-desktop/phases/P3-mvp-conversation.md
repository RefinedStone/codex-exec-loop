# P3. MVP 대화 화면

상태: 진행 중 (3단계: 마크다운과 긴 대화) · 기준일: 2026-11-05 · 규모: 2~3주

## 1. 목표

공식 Codex 앱의 대화 부분을 Akra Desktop 에서 쓸 수 있게 만든다. 완료 기준은
[01 배경과 목표](../01-background-and-goals.md) §5 의 MVP 성공 기준과 같다.

## 2. 선행 조건

- P2 완료
- 가짜 Gateway 픽스처: 일반 대화, 도구 실행, 승인 요청, 중단, 오류. P1 실측 녹화를 바탕으로 만든다.

## 3. 범위

| 범위 안 | 범위 밖 |
| --- | --- |
| 사이드바: Project 목록, Project 별 스레드 목록 | diff 보기 (R1) |
| 대화 화면: 기록 표시, 스트리밍, 아이템 종류별 표시 | 터미널, 브라우저 (R2, R3) |
| 입력: 새 턴, steer, 중단 | 하네스 기능 (R5) |
| 새 스레드: Project 와 cwd 선택 | 이미지 첨부 (필요하면 추가) |
| 승인 대화상자 (여러 창 포함) | 설정 화면 전체 (모델 선택만 포함) |
| 연결 상태, 오류 표시 | |
| 성능: 프레임 단위 묶음, 가상 스크롤 | |

## 4. 화면 구성

```text
+----------------+------------------------------------------------+
| Project A      |  스레드 제목                    [모델] [상태]   |
|   스레드 1     |------------------------------------------------|
|   스레드 2 (*) |  사용자 메시지                                  |
| Project B      |  에이전트 메시지 (마크다운, 코드 블록)            |
|   스레드 3     |  > 명령 실행: npm test        [출력 펼치기]      |
|                |  > 파일 변경: src/a.ts                          |
| [+ 새 스레드]  |  [승인 요청: 명령 실행 ... ] [허용] [거부]        |
|                |------------------------------------------------|
| 연결: 정상     |  입력창                         [보내기] [중단]  |
+----------------+------------------------------------------------+
```

(*) 진행 중인 스레드 표시

## 5. 상태 모델 (renderer)

| 저장소 | 내용 | 출처 |
| --- | --- | --- |
| connection | 연결 상태, codex 버전 | preload, `akra/gateway/info` |
| projects | Project 목록 | `project/list`, `project/changed` |
| threads | Project 별 스레드 요약 | `thread/list`, `thread/status/changed`, `thread/project/updated` |
| transcript | 스레드별 턴과 아이템 | `thread/resume` 결과 + `turn/*`, `item/*` 알림 |
| pendingRequests | 승인 요청 | 서버 요청, `serverRequest/resolved` |

- 상태 관리는 zustand 를 쓴다 (P-05).
- 원본은 app-server 이다 (D-05). renderer 상태는 화면용 사본이다. 불일치가 의심되면 `thread/read` 로
  다시 읽는다.

## 6. 동작 규칙

### 6.1 스레드 열기와 닫기

- 스레드를 열면 `thread/resume` 을 보낸다. 응답의 기록으로 화면을 그린다. 이후 알림을 반영한다.
- 다른 스레드로 이동하면 이전 스레드는 `thread/unsubscribe` 로 구독을 끝낸다. 단, 진행 중인 턴이 있는
  스레드는 알림 표시를 위해 구독을 유지할 수 있다 (구현 때 결정).

### 6.2 입력

| 상황 | 동작 |
| --- | --- |
| 턴이 없을 때 보내기 | `turn/start` |
| 턴 진행 중 보내기 | `turn/steer` |
| 중단 버튼 | `turn/interrupt` |
| 새 스레드 | `thread/start {projectId, cwd}` 다음 `turn/start` |

### 6.3 아이템 표시

| 아이템 | 표시 |
| --- | --- |
| agentMessage | 마크다운. delta 를 이어 붙인다 |
| reasoning | 요약만 접어서 표시한다 |
| commandExecution | 명령, 상태, 종료 코드. 출력은 접어서 표시하고 delta 를 이어 붙인다 |
| fileChange | 파일 목록과 변경 종류. 내용 diff 는 R1 에서 추가한다 |
| mcpToolCall | 도구 이름, 상태, 결과 요약 |
| plan | 계획 단계 목록과 진행 상태 |
| 기타 | 종류와 상태만 표시한다. 알 수 없는 종류에서 오류가 나지 않게 한다 |

### 6.4 승인 요청

- 서버 요청을 받으면 해당 스레드 화면과 사이드바에 표시한다.
- 응답 선택지는 요청의 params 에 있는 값만 쓴다.
- `serverRequest/resolved` 를 받으면 표시를 지운다. 다른 창에서 답한 경우도 같다.
- 거의 동시에 답했을 때의 처리는 Q-03 결과를 따른다.

### 6.5 오류와 재접속

- 접속이 끊기면 입력을 막고 상태를 표시한다.
- 다시 연결되면 initialize 를 하고 열려 있던 스레드를 `thread/resume` 한다. 대기 중인 승인 요청은
  replay 로 다시 온다.
- 턴 오류(`turn/completed` 의 실패 상태 등)는 대화 안에 표시한다.

## 7. 성능

화면의 부드러움은 전송보다 렌더링이 좌우한다 (D-09).

- delta 를 바로 그리지 않는다. 버퍼에 모아 `requestAnimationFrame` 마다 한 번 반영한다.
- 긴 대화는 보이는 부분만 그린다 (가상 스크롤).
- 마크다운 파싱은 완료된 블록을 캐시한다. 진행 중인 마지막 블록만 다시 파싱한다.
- 목표: 긴 응답 스트리밍 중에도 입력과 스크롤이 끊기지 않는다. 가짜 Gateway 로 빠른 delta 를 재생해서
  측정한다.

## 8. 시험

- 모든 화면 시험은 가짜 Gateway 로 한다. 턴을 쓰지 않는다 (D-13).
- 단위: 알림을 상태에 반영하는 함수, delta 묶음, 아이템 종류별 변환
- 화면: Playwright 로 Electron 을 실행한다. 스레드 열기, 스트리밍, 승인, 중단, 재접속을 재생한다.
- 여러 창: 창 두 개에 같은 스레드를 열고 승인 요청과 `serverRequest/resolved` 를 재생한다.

## 9. 완료 기준

1. 01 §5 의 성공 기준 1~5 를 가짜 Gateway 시험으로 확인한다.
2. 성공 기준 6 (앱을 닫은 뒤 턴 유지)은 Q-09 결과와 P1 의 대응으로 확인한다.
3. 사용자가 실제 업무 하루를 Akra Desktop 으로 처리하고 불편 목록을 남긴다. 이 목록이 R 단계의 순서를
   정한다.

## 10. 진행 기록

### 2026-11-05 1단계: 대화 보기

- 사이드바: `thread/list` 의 스레드를 작업 폴더(cwd)로 묶는다 (D-16). `thread/status/changed` 로 진행 중인
  스레드에 표시를 붙인다.
- 스레드 열기: `thread/resume` 응답으로 화면을 그리고, 그 스레드의 `turn/*`, `item/*` 알림을 반영한다. 다른
  스레드로 옮기면 진행 중인 턴이 없는 이전 스레드는 `thread/unsubscribe` 한다. 다시 연결되면 열린 스레드를
  다시 resume 한다. resume 응답을 기다리는 동안 온 알림은 응답을 반영한 뒤 이어서 반영한다.
- 상태 모델: `src/renderer/conversation/transcript.ts` 의 순수 함수. delta 는 agentMessage, commandExecution
  출력, plan, reasoning 요약에 이어 붙인다. 알림은 화면 프레임마다 한 번에 반영한다 (`FrameBatcher`).
- 아이템 표시: userMessage, agentMessage(일반 텍스트), reasoning(요약 접기), commandExecution(명령·상태·exit·출력
  접기), fileChange(파일 목록), mcpToolCall, plan, 그 밖의 종류(종류와 상태만).
- 가짜 Gateway 는 녹화를 순서대로 재생한다. 요청에 답한 뒤 녹화에서 그 다음에 온 알림과 서버 요청을 보내고,
  서버 요청에 대한 클라이언트 답을 받으면 그 뒤의 알림을 이어서 보낸다.
- 실기에서 찾은 문제: 긴 스레드의 `thread/resume` 응답이 Gateway 의 WebSocket 기본 한도(tungstenite 메시지
  64 MiB, 프레임 16 MiB)를 넘어 세션이 조용히 닫혔다. 한도를 256 MiB 로 올리고 읽기 오류를 로그에 남기게
  고쳤다 (별도 PR). 이 스레드는 여는 데 약 5.7초가 걸렸다. 긴 스레드는 7장의 가상 스크롤과 함께
  `excludeTurns`·페이지 읽기를 검토한다.
- (2단계에서 입력과 승인을 추가했다. 아래 참고.)

### 2026-11-05 2단계: 입력과 승인

- 입력창: Enter 보내기, Shift+Enter 줄바꿈. 턴이 없으면 `turn/start`, 진행 중이면 `turn/steer`
  (`expectedTurnId` = 진행 중인 턴), 중단 버튼은 `turn/interrupt`. 연결이 끊기면 입력을 막는다.
- 새 스레드: 사이드바 작업 폴더의 `+` 가 `thread/start {cwd}` 를 보내고 그 스레드를 연다 (D-16). 첫 메시지는
  입력창으로 보낸다.
- 승인: `item/commandExecution/requestApproval`, `item/fileChange/requestApproval` 을 열린 스레드 화면과 사이드바
  (`승인` 표시)에 보여 준다. 선택지는 허용, 이 세션 동안 허용, 거부이다. codex 0.159 의 안정 API 는 요청에
  선택지 목록을 주지 않아서 §6.4 의 "params 의 값만 쓴다" 대신 응답 타입이 정한 값 중 세 가지를 쓴다.
  `serverRequest/resolved` 를 받으면 응답 없이 지운다 (Q-03). 연결이 끊기면 대기 중 승인을 지우고, 다시
  구독하면 replay 로 다시 받는다. 그 밖의 서버 요청(권한, 사용자 입력, MCP elicitation)은 아직 method not found
  로 답한다.
- `AKRA_GATEWAY_ENDPOINT` 로 앱을 가짜 Gateway 에 붙일 수 있다. `npm run e2e` 가 빌드한 앱으로 승인 흐름(사이드바
  → 스레드 → replay 된 승인 → 허용 → 턴 완료 → 입력창 상태)을 재생한다. Electron 실행 파일과 화면이 필요해서
  아직 CI 에는 넣지 않았다.
- 남은 일: 마크다운, 가상 스크롤과 긴 스레드 페이지 읽기, 여러 창 승인 시험, 화면 시험의 CI 실행, 실제 턴으로
  입력 확인 (턴 사용 허락 필요).

### 2026-11-05 3단계: 마크다운과 긴 대화

- 에이전트 메시지를 마크다운(react-markdown 10.1.0 + remark-gfm)으로 그린다. 원시 HTML 은 그리지 않는다. 링크는
  새 창으로 열어 main 이 기본 브라우저로 넘긴다. 아이템과 턴은 `memo` 로 감싸서, 상태 모델이 바꾼 아이템만 다시
  그린다. 스트리밍 중인 메시지는 매 프레임 전체를 다시 파싱한다 (`shortcut:` 주석, 느려지면 블록 캐시).
- 가상 스크롤(@tanstack/react-virtual 3.14.26): 보이는 턴만 그린다. 맨 아래를 보고 있으면 새 내용을 따라가고,
  위로 올려 읽는 중이면 따라가지 않는다. 스레드를 새로 열면 최근 턴부터 보여 준다.
- 실측 (Windows 11, 실제 스레드 6개, `thread/resume` 만): 전체 높이 185,051px 스레드에서 실제로 그린 턴은 4개,
  DOM 노드 3,671개였다. 여는 시간은 233ms~2.4s, 가장 큰 스레드는 4.5s 로, 그리는 시간보다 응답 전송과 파싱이
  대부분이다. 큰 스레드는 `excludeTurns` 와 `thread/items/list` 페이지 읽기로 줄이는 것을 다음 일로 둔다.
- 남은 일: 큰 스레드 페이지 읽기, 여러 창 승인 시험, 화면 시험의 CI 실행, 실제 턴으로 입력 확인 (턴 사용 허락
  필요), macOS 실기 확인.

### 2026-11-05 리뷰 후속 (머지된 PR 의 Codex 리뷰 지적)

- 접속 시작: main 이 `did-finish-load` 에서 접속하면, 빠른 `connected` 알림이 renderer 의 수신 함수 등록 전에 와서
  사라질 수 있었다. renderer 가 수신 함수를 등록한 뒤 `window.akra.ready()` 를 보내고, main 은 그때 접속을
  (다시) 연다. P2 §4.4 의 브리지는 함수 5개가 되었다 (`ready`, `chooseFolder` 추가).
- 사이드바: `thread/list` 의 `nextCursor` 를 따라 모든 페이지를 읽는다 (최대 50 페이지). 목록의 `status` 로
  진행 중 표시를 처음부터 채운다. 스레드가 없는 새 설치에서도 `+ 폴더를 골라 새 스레드` (시스템 폴더 선택)로
  시작할 수 있다.
- resume 알림 버퍼를 요청별로 분리했다. 빠르게 스레드를 바꿔도 먼저 끝난 resume 이 새 스레드의 버퍼를 지우지
  않는다.
- 승인: `kind: "writeStdin"` 은 "실행 중인 프로세스에 입력 보내기 승인" 으로 따로 보여 준다.
- 녹화 정리 스크립트는 허용 목록의 구조 키만 원문을 남긴다. 토큰처럼 보이는 짧은 값도 다른 키 아래에 있으면
  바꾼다.

### 2026-11-05 큰 스레드 페이지 읽기

- 실측 (Windows 11, 실제 스레드 8개, 조회만): 가장 큰 스레드의 전체 `thread/resume` 은 30.8 MB, 1.35~2.7s 였다.
  `excludeTurns: true` resume 은 4~6 KB, 약 6ms 이고, `thread/turns/list` 최신 10턴(`itemsView: "full"`)은
  11 MB, 270ms 였다 (요약 보기는 14 KB 지만 명령 출력 등이 빠진다).
- 스레드를 열면 턴 없이 resume 해서 구독하고, 최신 10턴을 읽는다. 대화 위쪽의 "이전 턴 더 보기" 가 다음
  페이지를 앞에 붙이고, 보던 턴 위치를 유지한다. 더 읽을 턴이 없으면 버튼이 사라진다. 아직 기록이 없는 새
  스레드의 목록 오류는 빈 기록으로 본다. 서버가 resume 에 턴을 함께 보내면(녹화 재생) 그대로 쓴다.
- 앱 실측: 스레드 6개를 여는 데 0.4~1.1s (처음 연 스레드는 준비 시간 포함 2.4s). 이전 턴 한 페이지는 227ms.
