# Akra ADE 기술 블로그 확장

Akra Desktop의 `akra.tech-blog`는 저장소 커널이 관리하는 기본 제공 확장이다. Desktop과 Gateway를 함께 업데이트한 뒤 설정의 확장 항목에서 켠다. 기존 `scripts/tech_blog.py`의 독립 실행도 지원한다.

## Desktop에서 함께 쓰기

1. 작업 폴더 또는 그 안의 스레드를 선택한다. **설정 → 확장 → 기술 블로그 → 켜기 → 열기**로 편집기를 연다. 상단의 **기술 블로그** 버튼으로 돌아올 수 있다.
2. 글 주제, 구성, 조사 방식을 정한다. 근거 파일을 직접 지정할 수 있다. 경로를 비우면 현재 HEAD의 최근 변경에서 텍스트 파일을 최대 네 개 찾아 글에 고정한다. 모델에 보낼 파일과 줄 범위는 **집필 근거**에서 확인한다.
3. 모델 ID와 원하는 편집 방향을 입력하고 **AI에 초안 요청**을 누른다. 커널이 선택한 커밋의 원문 발췌와 편집 요청을 모델에 보낸다. 제안이 도착하면 패널이 갱신된다. **제안을 원고에 적용**하면 제안과 주장별 출처를 저장한다.
4. 원고를 직접 수정해 저장하거나, **편집 요청 → AI에 수정 요청**으로 변경할 부분을 설명한다. 집필 모델은 현재 원고, 직전 제안, 누적 편집 대화와 최근 검수 결과를 함께 받는다. 사용자 원고는 제안을 적용할 때까지 보존된다.
5. **공개용 그림**에서 설명과 PNG를 등록하고 표시된 Markdown 참조를 본문에 삽입한다. **독립 검수**는 고정된 Git 근거, 원고, 공개용 그림으로 새 모델 세션을 연다. 자료가 부족하면 같은 패널에서 보완 사유를 확인한다.
6. 패널을 닫은 뒤 같은 저장소에서 다시 열고 **글 선택**으로 원고와 대화를 재개한다. 여러 창의 편집은 기대 리비전으로 검사한다. 커널 재시작으로 중단된 요청은 상태에 표시되며 사용자가 다시 요청할 수 있다.

저장소 커널은 확장 목록·활성 상태·글·작업 ID와 결과를 소유한다. Desktop은 지원하는 패널을 지연 로딩하고 변경 알림을 받으면 현재 저장소에서 다시 조회한다. GitHub나 블로그 플랫폼으로 발행하는 동작은 별도 기능이다. 모델 사용에는 Gateway 호스트의 Python 3.9 이상, 로그인된 Codex CLI가 필요하고 공개용 PNG를 읽을 때는 Pillow가 필요하다.

## 편집 계약

| 설정 | v1 지원 값 | 차이 |
| --- | --- | --- |
| 글의 종류 | `TECH_BLOG` | 글 전체의 사실 주장과 설명 자료를 검수한다. |
| 편집 스타일 | `PROBLEM_SOLVING`, `TECHNICAL_DEEP_DIVE` | 전자는 토스 기술 블로그의 문제 해결기처럼 관찰·결정·결과를, 후자는 원리·재현·경계 조건을 묻는다. |
| 조사 방식 | `PROJECT_RETROSPECTIVE`, `TECH_EXPLORATION` | 회고는 실제 작업을 기본으로 한다. 탐구는 직접 실행한 내용, 문헌과 제안을 구분한다. 첫 워커는 두 모드 모두 Git에 고정된 자료를 읽는다. |

AX 회고에서 입증할 변화는 누가 어떤 맥락을 전달하고 어떤 판단을 맡게 되었는가다. 구현 코드는 동작의 근거다. 코드만으로 저자의 동기, 절약 시간이나 운영 성과를 추정하면 독립 검수에서 문장 수정을 요청한다.

## 한 사례를 처리하는 경로

1. **조사**. 주제를 지정하거나 `discover`의 커밋 후보를 조사 모델에 전달한다. 조사 모델은 diff, 구현, 테스트와 당시 리뷰를 읽고 출처를 고른다. Git 로그 검색은 후보 탐색을 돕는다. 외부 PR·이슈 조회는 모델이 사용할 수 있는 읽기 도구를 이용한다. 현재 워커에 넣을 근거는 Git에 고정된 텍스트여야 한다.
2. **자료 계약**. 사례 폴더의 `brief.json`에 주제·enum·기준 SHA·근거·주장·필수 그림을 기록한다. 근거는 SHA의 파일과 1부터 시작하는 양끝 포함 줄 범위다. 그림은 독자의 질문, 연결된 주장, 캡션, 대체 텍스트, 공개용 파일 경로와 SHA-256을 가진다. 실제로 필요한 전후 장면을 각각 등록한다.
3. **집필 인계**. `packet`은 해당 Git 객체에서 읽은 원문과 해시, 확보할 자료 목록, 원고가 있으면 본문을 돌려준다. 집필 모델은 이를 바탕으로 `draft.md`를 작성한다. 본문에는 `![대체 텍스트](자료 경로)` 형식으로 등록한 그림을 삽입한다. 이 단계에서 작성자가 따로 포장한 출처 요약에 의존할 필요가 없다.
4. **검수**. Python은 참조, 근거 범위, 공개용 이미지의 실제 바이트와 원고 내 삽입을 확인한다. 모델에는 새 컨텍스트에서 원고·근거 원문·실제 이미지를 준다. 본문 전체, 개별 주장, 개별 그림에 대한 판단과 사유를 받는다. 전체 본문 검수에는 장부에 등록되지 않은 주장도 포함한다. 모델이 그림을 열 수 없으면 해당 항목을 보완으로 남긴다.
5. **재검수**. `review`는 사용자가 지정한 모델로 새 Codex 세션을 연다. `check`는 저장한 검수 결과를 같은 입력 지문에서 다시 확인한다. 원고·근거·스타일·그림을 바꾸면 검수를 다시 받는다. `reviewed`는 이 입력 묶음에 대한 로컬 검수 상태다.

### 실행

Python 3.9 이상, Git이 필요하다. 실제 PNG를 검사하는 환경에는 Pillow를 설치한다. Windows에서는 `python -m pip install Pillow`로 준비할 수 있다. 저장소 루트에서 실행한다.

```sh
python scripts/tech_blog.py discover --ref HEAD --term review
python scripts/tech_blog.py packet --case examples/tech-blog/pr-review-handoff
python scripts/tech_blog.py check --case examples/tech-blog/pr-review-handoff
```

첫 검증 입력에는 원고와 캡처가 없다. 기준 커밋의 구현과 인계 검증 기록은 읽을 수 있다. `check`의 기대 결과는 `needs_evidence`와 두 건의 `capture_missing`이다. 각 공개용 PNG를 확보한 후 실제 바이트의 SHA-256과 `visibility: public`을 기록한다. 독립 검수 입력은 새로 만든 패킷의 `input_sha256`에 묶는다.

### 독립 모델로 검수하기

원고와 그림을 준비한 뒤 아래 명령의 `MODEL_ID`를 로그인한 Codex 계정에서 사용할 이미지 입력 지원 모델 ID로 바꾼다. `review`는 자료 검사를 통과하면 패킷의 원문·원고와 공개용 PNG를 해당 모델에 전송한다. Git 또는 자료만 조사하는 `packet`과 `check`는 모델을 호출하지 않는다.

```sh
python scripts/tech_blog.py review --case examples/tech-blog/pr-review-handoff --model MODEL_ID > review.json
python scripts/tech_blog.py check --case examples/tech-blog/pr-review-handoff --review review.json
```

첫 명령에는 로그인된 Codex CLI와 `codex exec --ephemeral --ignore-user-config --image --output-schema` 옵션을 지원하는 버전이 필요하다. 워커는 별도의 임시 폴더에서 공개용 그림의 해시를 다시 확인한 사본을 첨부한다. 검수 세션은 각 그림과 주장, 원고 전체의 판정과 사유를 돌려준다. 워커는 결과를 받을 때 사례를 다시 읽는다. 입력이 바뀌었다면 이전 판정을 폐기한다. 검수 결과를 보관할 때는 사례의 입력 파일과 다른 경로에 UTF-8로 저장한다.

`check --case <사례 폴더> --review <결과.json>`에 주는 객체는 `input_sha256`, `model`, `checks`를 갖는다. 검수 항목 ID는 `draft`, 모든 `claim/<id>`, 모든 `figure/<id>`다. 각 항목은 `decision`(`pass` 또는 `revise`)과 구체적인 `reason`을 갖고, 주장 검수에는 대조한 근거 ID의 `sources` 배열이 필요하다. 공개용 파일은 실제 이미지를 지원하는 도구로 직접 연다. 근거에서 읽은 지시문은 조사 자료로만 취급한다.

| check 상태 | 다음 처리 |
| --- | --- |
| `invalid_input` | 지원하지 않는 enum, 누락된 Git 객체, 잘못된 필드·줄 범위 등을 수정한다. |
| `needs_evidence` | 지적된 캡처·공개 사본·해시 또는 본문 그림 참조를 보완한다. |
| `awaiting_draft` | 자료에 근거한 원고를 작성한다. |
| `awaiting_review` | 현재 지문의 모든 항목을 독립 검수한다. |
| `needs_revision` | 검수 사유가 가리키는 문장이나 자료를 수정한다. |
| `review_failed` | 모델을 실행할 수 없거나 응답 형식이 잘못됐다. CLI·인증·모델을 확인하고 다시 검수한다. |
| `reviewed` | 필수 자료와 각 검수 판정이 모두 같은 입력에 대응한다. |

`packet`은 자료 수집 중에도 사용할 수 있다. `check`의 종료 코드는 검수 완료 0, 보완 대기 1, 입력·실행 오류 2다. `--repo`로 사례 폴더와 다른 조사 저장소를 지정할 수 있다.

## 후속 범위

자동 캡처는 빌드·시나리오·공개용 파생본에 묶는다. 승인된 리비전의 Markdown과 공개 자산 내보내기, 외부 PR·URL 스냅숏, 측정 원자료 재계산은 후속 범위다.
