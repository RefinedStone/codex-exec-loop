## 한 줄 요약

지금의 블로그 기능은 사용자가 단계마다 값을 넣는 공동 편집기다. 이 계획은 그것을 "작업을 고르고 한 번 누르면 Akra 가
글을 만든다"로 바꾼다. 글쓰기 규칙은 스킬에 두고, 실행과 저장은 커널 확장(플러그인)이 맡는다. 화면은 결과를 먼저
보여준다.

## 1. 사용자가 원하는 것 (요청 2026-11-23)

- 플러그인처럼 붙는 자동 블로그 작성 기능이다. 구성은 스킬 + 플러그인이다.
- 사용자가 마감 단계와 모델을 직접 입력하지 않는다.
- 결과물이 무엇인지 바로 보인다.
- 화면과 사용자 흐름이 처음 보는 사람에게도 읽힌다.

"마감"이라는 낱말은 현재 화면에 없다. 이 문서는 "마감"을 검수와 완료 단계로 읽었다. 기한의 뜻이어도 결론은 같다.
새 화면에는 사용자가 넣는 마감 값이 없다.

## 2. 현재 구현 (PR `841c62bf`, 2026-11-23)

`akra.tech-blog` 확장은 명령 9개(`configure`, `create`, `open`, `list`, `save`, `figure`, `accept`, `write`, `review`)를
가진다. 화면은 `desktop/src/renderer/extensions/TechBlogPanel.tsx`, 처리는 `scripts/tech_blog_studio.py` 다.

검수를 통과한 글 1개를 얻으려면 사용자가 아래를 모두 한다. 값 입력은 최소 4개, 누르기는 최소 7회다.

1. 설정에서 확장을 켜고 패널을 연다.
2. 글 주제를 넣는다. 글의 구성, 조사 방식, 근거 파일 경로를 고른다. "글 만들기"를 누른다.
3. 모델 ID 를 글자로 넣는다. "AI에 초안 요청"을 누른다.
4. 끝날 때까지 기다린다. "제안을 원고에 적용"을 누른다.
5. 그림 설명을 넣고 PNG 를 고르고 "그림 등록"을 누른다. 표시된 Markdown 참조를 원고에 직접 붙이고 "수정 저장"을 누른다.
6. "독립 검수"를 누른다.
7. 결과가 "수정 요청"이면 3번부터 다시 한다.

이 뒤에도 글은 화면의 글상자와 런타임 DB 안에만 있다.

## 4. 설계 원칙

1. **입력 0개가 기본이다.** 대상은 미리 골라져 있다. 주제와 고쳐 쓰기 요청은 선택이다.
2. **화면 하나에 주 동작 하나.** 홈은 "글 만들기", 진행은 "취소", 결과는 "파일로 내보내기"다.
3. **결과가 먼저다.** 글은 그린 미리보기로 보인다. 검수, 근거, 기록은 접혀 있다.
4. **사람의 글을 지우지 않는다.** 다시 쓰기 전의 원고는 이전 판으로 남는다.
5. **모델 사용은 사람이 시작한다.** 자동으로 하는 것은 표시와 제안까지다. 모델 호출 횟수를 화면에 적는다.
6. **판정은 커널이 한다.** 상태, 단계, 읽음, 오류 코드는 커널의 값이다. Desktop 은 그리기만 한다 (plan 18).
7. **기존 부품을 쓴다.** 새 부품은 다른 방법이 없을 때만 만든다 (§7.0).

## 5. 용어

| 용어 | 뜻 |
| --- | --- |
| 글 | 확장이 가진 글 1개. 원고, 주장, 검수 결과, 기록을 가진다. |
| 대상 | 글의 재료가 되는 커밋의 모음. |
| 근거 | 대상 커밋의 메시지와 변경 내용. SHA 에 고정한다. |
| 검수 | 새 모델 세션이 원고와 근거를 대조하는 것. |
| 지적 | 검수가 "고쳐야 한다"고 답한 항목 1개. |
| 판 | 원고의 내용 판. 다시 쓰기와 직접 고치기가 새 판을 만든다. |
| 내보내기 | 글을 Markdown 파일로 쓰는 것. |

## 6. 사용자 흐름

```text
[설정 → 확장 → 켜기]  (저장소마다 처음 1회)
        │
        ▼
[위쪽 띠의 책 아이콘] ──▶ V1 홈 ──(준비 안 됨)──▶ V0 준비 안내
                           │
                 대상 확인 (미리 골라져 있음) → "글 만들기"
                           ▼
                        V2 진행 ──(취소 · 실패 · 중단)──▶ V2 멈춤 ── "이어서 하기" / "버리기"
                           │ 완료
                           ▼
                        V3 결과 ── "다시 쓰기" ──▶ V2 진행
                           │   └── "직접 고치기" ──▶ V4 편집 ── 저장 ──▶ V3 결과
                           ├── "Markdown 복사"
                           └── "파일로 내보내기" ──▶ 경로 표시 · "편집기로 열기"
```

### 6.1 흐름 A: 처음 사용

1. 사용자가 **설정 → 확장 → 기술 블로그 → 켜기**를 누른다. 위쪽 띠에 책 아이콘이 생긴다.
2. 사용자가 **열기** 또는 책 아이콘을 누른다. 오른쪽 패널에 V1 홈이 열린다.
3. Python, Git, Codex CLI 중 없는 것이 있으면 V0 준비 안내가 보인다. 없는 것과 조치를 한 줄씩 적는다. "다시 확인"을 누르면 다시 검사한다.
4. 준비가 됐으면 V1 홈이다. 글 목록이 비어 있으면 빈 상태 문구를 보인다 (§8.4).

### 6.2 흐름 B: 글 만들기 (핵심)

1. V1 홈에 최근 커밋 목록이 있다. 지난 글 뒤의 커밋이 미리 골라져 있다. 첫 글이면 최근 20개다.
2. 사용자가 필요하면 커밋을 빼거나 더한다. 주제 한 줄은 선택이다.
3. 사용자가 **글 만들기**를 누른다. 버튼 옆에 "모델 호출 2–4회"가 적혀 있다.
4. V2 진행이 열린다. 단계 4개(근거 모으기, 초안 쓰기, 검수, 고쳐 쓰기)와 경과 시간을 보인다.
5. 초안 쓰기가 끝나면 단계 아래에 초안이 보인다. "검수 중인 초안입니다. 바뀔 수 있습니다."를 함께 보인다.
6. 검수가 지적을 내면 Akra 가 1회 고쳐 쓰고 다시 검수한다. 사용자는 아무것도 누르지 않는다.
7. 끝나면 V3 결과로 바뀐다. 사용자가 누른 횟수는 1회다.

### 6.3 흐름 C: 결과 확인과 고치기

1. V3 결과는 제목, 상태 표시, 동작 줄, 미리보기 순서다.
2. 상태가 "검수 통과"이면 사용자는 읽고 내보낸다.
3. 상태가 "지적 n건"이면 지적 목록이 펼쳐져 있다. 사용자는 **지적 반영해 다시 쓰기**를 누르거나, 그대로 내보낸다.
4. 다른 방향을 원하면 **다시 쓰기…**를 누른다. 요청 한 줄을 넣거나 예시 칩("더 짧게", "더 자세히", "처음 보는 사람도 읽게")을 누른다.
5. 한두 문장만 고치려면 **직접 고치기**를 누른다. V4 편집에서 저장하면 상태가 "검수 안 함"이 된다. **검수하기**는 사용자가 누를 때만 돈다 (모델 호출 1회).
6. 다시 쓴 결과가 마음에 들지 않으면 **이전 판으로**를 누른다.

### 6.4 흐름 D: 내보내기

1. 사용자가 **파일로 내보내기**를 누른다.
2. Akra 가 작업 폴더에 `blog/<날짜>-<slug>/post.md` 를 쓴다. 등록한 그림은 같은 폴더에 쓴다.
3. 버튼 아래에 경로와 **편집기로 열기**가 생긴다. 변경 패널에는 새 파일로 보인다.
4. 내보낸 뒤에 글을 고치면 "내보낸 파일보다 새 판입니다"와 **다시 내보내기**를 보인다.
5. 커밋과 외부 발행은 사람이 한다.

### 6.5 흐름 E: 패널을 닫고 다른 일을 한다

1. 진행 중에 패널을 닫거나 다른 패널을 연다. 작업은 계속된다.
2. 책 아이콘에 진행 표시가 생긴다.
3. 끝나면 토스트 "블로그 글이 준비됐습니다."를 보이고, 책 아이콘의 표시가 "새 결과"로 바뀐다.
4. 앱이 뒤에 있으면 OS 알림을 보낸다. 알림에는 글의 제목과 내용을 넣지 않는다 (`views/notify.ts` 의 규칙).
5. 아이콘이나 알림을 누르면 그 글의 V3 결과가 열린다. 글을 열면 표시가 사라진다.

### 6.6 흐름 F: 취소, 실패, 중단

- **취소.** 사용자가 V2 에서 "취소"를 누른다. 다음 단계를 시작하지 않는다. 끝난 단계의 결과는 남는다.
- **실패.** 모델이 답하지 못하거나 시간을 넘긴다. V2 멈춤에 원인과 조치를 적는다 (§8.3).
- **중단.** 커널이 다시 시작됐다. 글 목록에 "멈춤"으로 보인다.
- 세 경우 모두 **이어서 하기**는 멈춘 단계부터 다시 한다. 끝난 단계의 모델 호출을 다시 쓰지 않는다. **버리기**는 글을 지운다.
- 초안이 이미 있으면 "초안 보기"로 읽고 복사할 수 있다.

### 6.7 흐름 G: 자동 표시 (후속, §13 Q4)

1. 지난 글 뒤에 커밋이 쌓이면 V1 홈의 대상에 이미 들어 있다. 추가 화면은 없다.
2. 설정에서 "새 작업 표시"를 켜면, 기준 수(제안값 10개)를 넘을 때 책 아이콘에 조용한 표시를 둔다.
3. 표시는 모델을 부르지 않는다. 글 만들기는 사람이 누른다.

### 6.8 경계 사례

| 사례 | 동작 |
| --- | --- |
| 지난 글 뒤에 새 커밋이 없다 | 아무것도 골라지지 않는다. 문구로 알리고 이전 커밋에서 고르게 한다. |
| 커밋하지 않은 변경이 있다 | 글에 넣지 않는다. 목록 아래에 한 줄로 알린다. |
| 고른 커밋이 30개를 넘는다 | "글 만들기"를 막고 한도를 알린다. |
| 근거가 크기 한도를 넘는다 | 큰 파일부터 요약 줄로 바꾼다. 진행 화면에 "요약만 넣은 파일 n개"를 적는다. |
| 같은 저장소에서 글을 만드는 중이다 | "글 만들기"를 막고 "다른 글을 만드는 중입니다"와 그 글로 가는 링크를 보인다. |
| 다른 창에서 같은 글을 바꿨다 | 최신 글을 다시 읽고 "다른 창에서 글이 바뀌었습니다"를 보인다. 편집 중인 글자는 지우지 않는다. |
| 진행 중에 확장을 끈다 | 작업을 멈춘다. 다시 켜면 "멈춤"으로 보인다. |
| 다른 저장소의 스레드로 옮긴다 | 패널은 그 저장소의 글 목록을 보인다. 이전 저장소의 작업은 계속된다. 완료 알림은 돌아왔을 때 표시로 보인다. |
| 버전 1 로 만든 글 | 열기, 복사, 내보내기를 할 수 있다. 다시 쓰기는 지원하지 않는다. |

## 7. 화면

### 7.0 공통

- 위치는 지금과 같은 오른쪽 패널이다. 폭은 360–900 px, 기본 520 px 이고, 최대화할 수 있다 (`App.tsx` 의 `RightPanel`).
- 패널의 화면은 4개다: V1 홈, V2 진행, V3 결과, V4 편집. V0 은 V1 의 자리에 나온다.
- V2–V4 의 맨 위에 "← 글 목록"이 있다. 누르면 V1 로 간다.
- 본문의 줄 길이는 최대화했을 때도 720 px 를 넘지 않는다.
- 쓰는 기존 부품:

| 필요 | 기존 부품 |
| --- | --- |

## 9. 구조: 스킬 + 플러그인

| 부분 | 맡는 일 | 위치 |
| --- | --- | --- |
| 스킬 | 글의 구성, 문체, 근거 규칙, 금지 사항. 사람이 읽고 고친다. | `assets/app-server/skills/akra-tech-blog/SKILL.md` (신규). `akra-issue-draft-review` 와 같은 방식이다. |
| 플러그인 (커널 확장) | 대상 목록, 근거 수집, 모델 실행, 검수 반복, 판, 읽음, 내보내기, 작업 상태. | 기존 `akra.tech-blog` 확장. 버전 2. |
| Desktop 패널 | 대상 고르기, 진행 표시, 결과 보기. 판단을 하지 않는다. | `TechBlogPanel.tsx` |

### 9.1 모델

- 사용자가 모델을 넣지 않는다. 워커는 `--model` 을 주지 않고 Codex 의 기본 모델을 쓴다.
- 검수는 같은 모델의 새 세션으로 한다. 지금도 `codex exec --ephemeral` 이므로 세션은 독립이다.
- 모델을 바꾸는 설정은 이 계획에 넣지 않는다. 필요가 확인되면 "설정 → 확장"에 값 1개를 더한다.

### 9.2 대상과 근거

- 대상은 커밋 SHA 의 목록이다 (1–30개). 이어진 범위가 아니어도 된다.
- `targets` 명령은 최근 커밋과 "지난 글의 가장 새 커밋"을 준다. 모델을 부르지 않는다.
- 근거는 커밋마다 메시지와 변경 내용이다. 모두 SHA 에 고정한다.
- 크기 한도(제안값): 전체 200 KB, 커밋당 40 KB. 넘으면 큰 파일부터 요약 줄(`--stat`)로 바꾼다.
- 스킬은 대상에서 주제 하나를 고르게 한다. 모델은 쓴 커밋과 쓰지 않은 커밋을 답에 적는다.
- 주장마다 근거 ID 를 붙이는 현재 계약과 지문(`input_sha256`) 검사는 그대로 쓴다.
- 저장소 안의 파일을 지시문으로 읽지 않는다. 워커는 지금도 붙은 저장소의 파일과 독립으로 돈다 (`tech_blog_worker.rs:1`). 근거 안의 지시는 자료로 다룬다.

### 9.3 단계 실행

- 지금은 작업 1개가 워커 호출 1회이고 제한은 640초다. 모델 호출 1회의 제한은 600초다. 여러 단계를 호출 1회에 넣을 수 없다.
- 새 방식: 워커 호출 1회가 단계 1개를 한다. 워커는 단계의 결과와 다음 단계를 글에 적는다. 호스트(`repository_extensions.rs`)는 작업이 남아 있으면 다시 부른다.
- 호스트는 단계가 끝날 때마다 `changed` 를 보낸다. 화면의 단계 표시는 이것으로 갱신된다.
- "이어서 하기"는 글에 적힌 단계부터 다시 부른다.
- 취소는 다음 단계를 막는다. 진행 중인 모델 호출은 끝까지 갈 수 있고, 그 결과는 버린다. 모델 프로세스를 바로 끝내는 것은 후속 조각이다 (§11 B7).
- 저장소 하나에서 동시에 도는 작업은 1개다.

### 9.4 검수와 마감

- 초안 뒤에 검수를 자동으로 한다. 지적이 있으면 사유를 넣어 1회 고쳐 쓰고 다시 검수한다.
- 모델 호출은 글 1개에 2–4회다: 초안 1, 검수 1, (지적이 있으면) 고쳐 쓰기 1, 검수 1.
- 그 뒤에도 지적이 남으면 글을 버리지 않는다. 상태는 `findings` 이고, 다음 고쳐 쓰기는 사람이 누른다.
- 그림은 선택이다. 그림이 없는 글도 `reviewed` 가 된다. 등록한 그림이 있으면 현재 검사를 그대로 적용한다.
- 사람이 고친 원고는 자동으로 검수하지 않는다.

### 9.5 판, 결과물, 내보내기

- 원본은 지금처럼 커널의 `tech-blog.sqlite3` 다. 화면의 결과는 이 원본을 그린 것이다.
- 다시 쓰기와 직접 고치기는 새 판을 만든다. 직전 판 1개를 남긴다. "이전 판으로"는 그 판을 되살린다.
- 내보내기는 사람이 누를 때 한다. 경로는 `<작업 폴더>/blog/<날짜>-<slug>/post.md` 다. 그림은 같은 폴더에 쓴다.
- `post.md` 머리말: 제목, 날짜, 대상 커밋, 검수 상태, 글 ID.
- slug 는 모델이 준 영문 값이다 (`[a-z0-9-]`, 3–60자). 맞지 않으면 글 ID 의 앞 8자를 쓴다.
- 같은 경로에 파일이 있으면 머리말의 글 ID 를 본다. 같은 글이면 덮어쓴다. 다르면 거절한다 (`export_exists`).
- 내보내기는 `blog/` 아래에만 쓴다. 심볼릭 링크를 따라가지 않는다. 확장의 권한에 `workspace.write` 를 더한다.
- 외부 발행(GitHub, 블로그 플랫폼)은 이 계획 밖이다.

### 9.7 지우는 것

- 화면: 모델 ID 입력, 글의 구성, 조사 방식, 근거 파일 경로, "제안을 원고에 적용", "독립 검수" 버튼, 글 선택 상자.
- 글의 구성과 조사 방식은 스킬이 대상의 내용으로 정한다.
- 제안과 적용의 두 단계는 판으로 바꾼다.
- `scripts/tech_blog.py` 의 독립 실행(`discover`, `packet`, `check`, `review`)은 바꾸지 않는다.
- Desktop 과 Gateway 의 버전이 다르면 패널은 보이지 않는다 (지금의 버전 대조). 둘을 함께 올린다.

## 10. 접근성과 키보드

- 패널은 지금처럼 이름이 있는 영역이다 (`aria-label="기술 블로그"`).
- 단계 목록은 순서 목록이다. 지금 단계에 `aria-current="step"` 을 둔다. 단계가 바뀌면 `role="status"` 영역이 한 문장으로 알린다.
- 완료 때 초점은 패널 안에 있을 때만 결과 제목으로 옮긴다. 다른 곳의 초점은 빼앗지 않는다.
- 오류는 `role="alert"` 이다. 상태 표시는 색과 글자를 함께 쓴다.
- 아이콘만 있는 버튼은 이름을 가진다. 꺼진 버튼은 이유를 옆의 글로 적는다.
- 요청 상자는 `⌘Enter` 로 보낸다. `Esc` 는 요청 상자를 닫는다.
- 폭 360 px 에서 가로 스크롤이 없다. 버튼 줄은 접히고 긴 경로는 줄을 바꾼다.

## 12. 위험

- `--ignore-user-config` 때문에 워커는 사용자의 Codex 설정을 읽지 않는다. 기본 모델과 접속 경로가 일반 대화와 다를 수 있다. B1 에서 실제 환경 1회로 확인한다. 이 확인은 모델 턴을 쓰므로 사용자 허락이 필요하다.
- 걸리는 시간을 재지 않았다. 화면은 남은 시간을 약속하지 않는다. 위의 실제 1회에서 단계별 시간을 적는다.
- 커밋 근거는 파일 발췌보다 크다. 한도 값은 제안값이고, 실제 1회의 사용량을 보고 정한다.
- 변경 내용이 모델로 간다. 커밋에 비밀 값이 있으면 함께 간다. V1 의 버튼 옆에 보내는 것을 적는다.
- 공개 저장소다. 자동 글에 내부 이름이 들어갈 수 있다. 내보낸 파일은 추적하지 않는 새 파일이고, 커밋과 발행은 사람이 한다.
- 취소는 B7 전까지 진행 중인 모델 호출 1회를 막지 못한다. 화면이 이것을 말한다.
- 모델이 고른 주제가 사용자의 뜻과 다를 수 있다. 주제 입력과 "다시 쓰기"로 고친다.
- 문체를 저장소마다 바꾸는 방법은 이 계획에 없다. 저장소의 파일을 지시문으로 읽으면 신뢰 경계가 깨진다 (§9.2). 필요하면 Akra 홈의 사용자 스킬로 따로 설계한다.
