# Akra 관찰-제안 구조 (전체 그림)

## 문서 상태

- 상태: **Proposed overview**. 2026-11-09 사용자와 논의한 방향을 한 장으로 정리했다. 세부 설계와 단계는 아직 없다.
  현재 제품 동작을 설명하지 않는다.
- 목적: 작업자와 사용자가 **전체 그림을 같은 모양으로 인지**하게 한다. 구현 순서와 세부 계약은 이 문서를 바탕으로
  plan 17, 18, 19 의 해당 단계에서 정한다.
- 관련 계획: [17 Akra Desktop](17-akra-desktop/README.md), [18 Akra 커널 아키텍처](18-akra-kernel-architecture.md),
  [19 Akra 커널 성질 목표](19-akra-kernel-quality-goals.md), [K3 커널 데몬](18-k3-kernel-daemon-protocol.md).
- 기준일: 2026-11-09 (Asia/Seoul)
- 기준 커밋: `838406dc` (`origin/prerelease`).

## 1. 사용자가 원하는 것

> 사용자는 Akra Desktop 을 Codex 앱처럼 **단순한 대화**로 쓴다. 그 대화에서 일이 생기거나 문제가 생기면, Akra 가
> 그것을 알아채고 **Akra↔사용자 양방향 프로토콜**로 제안하고, 묻고, 답에 따라 Akra 기능을 실행한다.

예:

- 대화에서 PR 을 만들었다 → "Akra PR 승인 흐름에 등록할까요?"
- 영상 편집 작업을 하고 있다 → "튜닝된 영상 편집 리뷰 에이전트에게 리뷰를 맡길까요?"
- 같은 시험이 계속 실패한다 → "원인 분석 턴을 이 대화에 넣을까요?"

## 2. 지금 상태와 차이 (2026-11-09)

```text
TUI ──── 프로세스 안 ──→ [자기 커널] ──→ 자기 전용 app-server        Akra 기능 있음, 턴은 한 번에 하나
Desktop ─ gateway.sock ─→ Gateway (단순 중계) ──→ Gateway 의 app-server  Akra 기능 없음, 커널이 대화를 모름
```

- Desktop 의 대화는 커널을 거치지 않는다. 그래서 대화 중 문제가 생겨도 Akra 가 자동으로 반응할 수 없다.
- TUI 와 Desktop 은 같은 입구를 쓰지 않는다. 목표(plan 18 KP-04)는 같은 입구이고, 지금은 이행 중이다.

## 3. 핵심 결정 (제안): 기록은 Codex, 관제와 주의는 Akra

"대화를 소유한다"는 말에는 세 층이 있다.

| 층 | 뜻 | 주인 | 이유 |
| --- | --- | --- | --- |
| 기록 | 메시지, 도구 실행, 턴 이력의 원본 | **Codex (app-server)** | 복사하면 두 기록이 어긋난다. resume, fork, compact, `thread/read` 는 Codex 가 제공한다 (plan 17 결정 A+) |
| 관제 | 모든 대화의 시작·종료·실패·승인을 빠짐없이 알고, 필요하면 개입(steer, 중단, 후속 턴, 위임)하는 권한 | **Akra 커널** | 이것이 없으면 "문제가 생기면 자동으로"가 불가능하다 |
| 주의 | Akra 가 사용자에게 알리고, 묻고, 제안하고, 답을 받는 메시지 | **Akra 커널** (Akra 사건 기록, plan 19 §5.1) | Codex 기록에 섞지 않는다. 화면에서만 대화 흐름 안에 함께 보인다 |

이 결정을 plan 17 의 **D-18 (제안)** 으로 둔다. Akra 가 기록까지 소유할 필요는 없다. 기록을 고쳐 써야 할 때(자체
compact)는 fork, `inject_items`, `developer_instructions` 로 하고, Codex 와 Claude 를 함께 보여 줄 때(R7)는 Akra 가
읽기용 투영만 만든다.

## 4. 목표 구조

```text
사용자 ── Desktop ──(일반 대화: 직접, 동시 실행 그대로)──→ Gateway ──→ app-server (기록, 1개 공유)
            ▲                                             │ 탭: 지나가는 메시지의 사본
            │ Akra 메시지 (알림·질문·제안·결과)             ▼
            └──────────── akra/kernel/* ←─────────── Akra 커널 (관제·주의, 저장소당 1개)
                                                       ① 관찰   모든 thread 의 사건
                                                       ② 인식   무슨 일이 일어나는가
                                                       ③ 카탈로그 맞는 기능·에이전트는 무엇인가
                                                       ④ 정책   묻기 / 자동 / 무시
                                                       ⑤ 실행   커널 명령, 위임 thread
                                                       ⑥ 반환   결과를 원래 대화에
```

| 부품 | 하는 일 | 비고 |
| --- | --- | --- |
| Gateway 탭 | 클라이언트와 app-server 사이의 메시지를 바꾸지 않고 사본을 커널에 넘긴다 | 일반 대화의 속도와 동시성을 그대로 둔다 |
| 관찰자 모드 | 커널이 자기가 시작하지 않은 턴(사용자 턴)도 추적한다 | 지금 core 는 자기가 낸 턴만 추적한다. 관찰한 턴은 커널의 "대화 턴 하나" 자리(K2 §3.3)를 차지하지 않는다. 그 자리는 커널이 시작한 턴만 쓴다. 그렇지 않으면 Desktop 의 동시 사용자 턴이 커널 제출을 계속 막는다. 커널이 관찰 중인 thread 에 후속 턴을 내려면 그 thread 의 턴이 끝나기를 기다린다 |
| app-server 공유 | 커널의 개입이 사용자가 보는 바로 그 thread 에 닿는다 | 커널과 Gateway 가 같은 app-server 를 쓴다. plan 17 P-08(TUI·하네스는 자체 app-server)을 다시 본다 |
| 인식기 | 결정적 신호(명령, 파일, 도구 사건, GitHub 상태)를 먼저 쓴다. 애매할 때만 의미 추론(대화 주제 분류)을 쓴다 | 의미 추론은 모델 비용이 든다. 턴 종료 시에만, 작은 모델로 한다 (plan 17 D-13) |
| 기능 카탈로그 | Akra 기능과 튜닝된 에이전트가 **"언제 나를 부를지"**(주제 태그, 파일 형식, 명령 패턴, 예시)를 선언하고 등록한다 | 새 기능이나 에이전트는 등록만 하면 된다. 스킬이 description 으로 선택되는 방식과 같다 |
| 정책 | 사용자 선택(이번만, 항상, 다시 묻지 않기), 신뢰도 기준, 대화당 제안 상한 | 제안이 많으면 사용자가 무시하게 된다 |
| 실행 | 커널 명령(PR 등록, 큐 추가) 또는 위임 thread(그 에이전트의 지침·모델·도구로 새 thread) | 위임 thread 는 원래 대화를 막지 않는다. 동시 실행은 plan 19 P4 또는 병렬 모드 슬롯이 맡는다 |
| 반환 | 결과를 원래 대화에 Akra 메시지로 보인다. 모델이 알아야 하면 `inject_items` 로 맥락에 넣는다 | - |
| 학습 고리 | 제안의 수락·무시, 리뷰의 채택 여부를 에이전트 튜닝 자료로 돌려준다 | 튜닝 시스템과 연결 방식은 미정 (§7) |

### 4.1 관찰 출처와 사건 기록 한 곳 (제안, 2026-11-11)

사용자의 방향: 대화뿐 아니라 git 과 파일시스템의 변경도 Akra 가 알아야 한다. 수퍼에이전트(여러 기능과 에이전트를
스스로 고르고 부르는 주체)가 이 신호로 움직인다. 아래는 그 자리를 정한 것이다. 구현은 없다.

```text
출처 (관찰자, 저장소당)                      한 곳                     소비자
┌ 대화 기록 ── 주소 인식기 (plan 22, 있음) ┐
├ git ── 커밋, 브랜치, 작업 폴더 상태       ├─▶ kernel 사건 기록 (K5) ─┬▶ 인식기와 정책 → 제안
├ 파일시스템 ── 바뀐 경로                   │    커서로 구독           ├▶ 기능 카탈로그 → 수퍼에이전트
└ GitHub ── PR, CI (폴링, 있음)             ┘                          └▶ 작업 컨텍스트 (path 범위 연결)
```

- **언급된 대상과 일어난 사건은 다르다.** 외부 문서는 대화에 언급된 대상이고 상태(지금 버전)로 다룬다. git 과 파일
  변경은 저장소에서 일어난 사건이고 순서로 다룬다. 사건은 plan 22 의 장부에 넣지 않는다.
- **사건은 한 곳에 쌓는다.** 출처마다 저장소를 따로 만들지 않는다. 모든 관찰자의 사건이 kernel 의 사건 기록
  (plan 18 K5, plan 19 Q3)에 들어가고, 소비자는 커서로 읽는다 (Q3-3b). 승인 기록(Q3-5)을 K5 설계로 미룬 이유와 같다.
- **관찰자는 사건만 낸다.** 출처 하나가 outbound 경계 하나이다. 판단(무슨 일인가, 무엇을 할까)은 인식기와 정책이
  한다. 새 출처는 관찰자 하나를 더하는 일이고, 소비자는 사건의 종류만 다룬다.
- **화면이 없어도 관찰한다.** 지금 문서의 "바뀜" 확인은 Desktop 이 요청할 때만 실행된다 (plan 22 2단계). 수퍼에이전트가
  쓰려면 상주하는 주인이 마감 시각(Q3-4)에 맞춰 시작해야 한다. 주인이 Gateway 인지 kernel 인지는 미정이다.

순서 (제안):

1. K5 설계에서 사건의 모양을 먼저 정한다: 종류, 출처, 대상, 시각, 멱등 키. 승인 객체(Q3-5)와 연산 영수증(Q3-6)을
   함께 정한다.
2. git 관찰자를 첫 출처로 더한다. 신호가 명확하고(커밋, 브랜치), 확인 비용이 낮고, §6.1 의 PR 사례와 바로 이어진다.
3. 파일시스템 관찰자는 그 뒤이다. 감시 범위(무시 규칙, 빌드 산출물), 사건의 양, 플랫폼 차이를 먼저 정해야 한다.

## 6. 사례

### 6.1 PR (첫 구현 사례로 제안)

1. 사용자가 일반 대화에서 PR 을 만든다. Codex 가 `gh pr create` 를 실행한다.
2. 인식: 도구 실행 결과의 PR URL, Akra GitHub 폴링이 본 새 PR 의 head 브랜치와 대화 작업 폴더의 브랜치. 두 신호가
   맞으면 PR 생성으로 본다. 모델 답변 문장만으로는 판단하지 않는다.
3. 제안: "PR #123 이 만들어졌습니다. Akra PR 승인 흐름에 등록할까요? [등록] [이번만 무시] [이 저장소는 항상 등록]"
4. 실행: PR 등록, CI 감시, 리뷰 대응, 머지 뒤 검증 (Akra 의 기존 PR 기능을 커널 명령으로 노출).
5. 이후: CI 실패나 리뷰 지적이 생기면 같은 대화에 다시 묻는다.

### 6.2 튜닝된 에이전트에게 리뷰 위임

1. 사용자가 영상 편집 작업을 한다 (ffmpeg 실행, `*.mp4`·`*.prproj` 파일).
2. 인식: 결정적 신호로 주제를 "영상 편집"으로 본다. 애매하면 대화 요약으로 분류한다.
3. 카탈로그: 트리거가 맞는 튜닝된 에이전트 "영상 편집 리뷰"를 찾는다.
4. 제안: "튜닝된 영상 편집 리뷰 에이전트에게 리뷰를 맡길까요?"
5. 실행: 그 에이전트의 프로필로 리뷰 thread 를 만들고, 대화 요약, 변경 파일, 실행한 명령을 맥락으로 넘긴다.
6. 반환: 리뷰 결과를 원래 대화에 보인다. 채택 여부를 튜닝 자료로 남긴다.
