# 27. Akra git 그래프 (커밋 그래프 보기와 git 작업 엔진)

상태: **Proposed**. 현재 제품 동작을 설명하지 않는다. · 기준일: 2026-11-18 (Asia/Seoul) ·
기준 커밋: `facaf9ed` (`origin/prerelease`) ·
관련: [plan 17 Akra Desktop](17-akra-desktop/README.md), [plan 18 kernel](18-akra-kernel-architecture.md),
[plan 20 관찰과 제안](20-akra-observe-and-offer.md), [plan 26 Desktop 사용성](26-akra-desktop-usability.md)

## 한 줄 요약

Akra 에 커밋 그래프 화면과 git 작업 엔진을 넣는다. 목표는 보기만 하는 화면이 아니다. 사용자는 그래프의 커밋을
가리켜 브랜치를 옮기고(hard reset), 커밋을 골라 cherry-pick 하고, 강제 push 를 안전하게 한다. 모든 작업은
계획으로 먼저 보이고, 백업이 있고, 되돌릴 수 있다.

## 범위

- 대상은 Akra 데몬(Gateway)의 git 서비스와 `desktop/` 의 그래프 화면이다.
- 목표 수준은 전용 git GUI 클라이언트의 일상 작업이다. 다른 제품의 코드를 옮기지 않는다. 다른 제품을
  조사하지 않았다. 이 문서의 동작은 사용자와의 설계 대화(2026-11-18)에서 정했다.
- 모델 턴이 필요한 동작은 사용자가 시작할 때만 한다.

## 1. 결정 (2026-11-18)

| ID | 결정 | 상태 |
| --- | --- | --- |
| G-1 | 강제 push 를 허용한다. 조건: sha 를 명시한 lease, Akra 보호 브랜치 목록의 거절, 항상 확인. 지금의 `desktop/src/main/gitPublish.ts` 규칙("강제 push 는 하지 않는다")을 바꾼다 | 사용자 결정 |
| G-2 | Akra 가 보호 브랜치 목록을 따로 관리한다. GitHub 의 보호 규칙과 독립이고 추가이다 (§5) | 사용자 결정 |
| G-3 | 파괴적 작업 전에 사용자 저장소에 백업 ref `refs/akra/backup/*` 를 쓴다 (§3.2) | 사용자 결정 |
| G-4 | git 서비스는 Rust 데몬에 둔다. Desktop 은 그리기만 한다 | 기본값. 사용자의 반대가 없었다 |
| G-5 | 화면은 오른쪽 패널이고 최대화할 수 있다 | 기본값. 사용자의 반대가 없었다 |
| G-6 | 엔진은 `git` CLI 이다. git 라이브러리는 측정으로 필요가 확인될 때만 읽기 경로에 넣는다 | 기본값 |

G-4 의 이유: kernel 은 어떤 worktree 에서 에이전트 턴이 실행 중인지 안다. 쓰기 작업은 이 정보로 막아야 한다.
TUI 와 CLI 가 같은 서비스를 다시 쓴다. Electron 없이 시험할 수 있다.

G-6 의 이유: CLI 는 hook, 자격 증명, LFS, sparse checkout, worktree 를 그대로 지원한다. 읽기 속도는
commit-graph 파일이 있으면 CLI 로 충분할 가능성이 높다. 이것은 측정하지 않았다 (§8).

## 2. 현재 상태 (2026-11-18, 소스 읽기)

- Desktop main 프로세스가 `git` CLI 를 직접 부른다: `desktop/src/main/gitStatus.ts`, `gitBranch.ts`,
  `gitHunks.ts`, `gitPublish.ts`.
- `gitPublish.ts` 는 계획(`planPush`)과 실행(`executePush`)을 나눈다. 실행은 계획과 현재 상태를 다시 비교한다.
  이 문서의 작업 엔진은 이 패턴을 모든 쓰기 작업으로 넓힌다.
- Rust 는 `src/git_subprocess.rs` 로 `git` CLI 를 부른다. git 라이브러리(`git2`, `gix`)는 의존성에 없다.
- Desktop 에 `@tanstack/react-virtual` 과 diff 보기(`conversation/DiffView.tsx`)가 있다.
- 커밋 그래프 화면은 없다. 브랜치의 커밋 목록(`conversation/BranchCommits.tsx`)만 있다.

## 3. 원칙

### 3.1 모든 쓰기 작업은 계획이다

- 작업은 계획을 만든다: 기대 상태, 단계 목록, 영향 미리보기.
- 실행은 기대 상태를 다시 검사한다: HEAD sha, 브랜치 sha, 원격 추적 sha, 작업 트리 상태, 보호 목록 버전.
- 상태가 계획과 다르면 실행하지 않는다. 사용자는 다시 계획을 본다.

### 3.2 파괴적 작업 전에 백업 ref 를 쓴다

- 이름은 `refs/akra/backup/<branch>/<op-id>` 이다.
- 이 ref 는 push 되지 않는다. push 는 항상 refspec 을 명시한다.
- 이 ref 가 있으면 `git gc` 가 커밋을 지우지 않는다.
- 그래프는 백업 ref 를 그린다. hard reset 뒤에도 예전 커밋이 흐린 색으로 남는다. push 하지 않은 브랜치는
  이것이 없으면 reset 뒤에 cherry-pick 할 커밋이 화면에서 사라진다.
- 정리: 브랜치마다 최근 N 개, 기간 D 일. 값은 설정이다. 기본값은 G4 에서 정한다.

### 3.3 확인의 양은 되돌릴 수 없는 정도에 비례한다

| 작업의 종류 | 확인 |
| --- | --- |
| 백업이 있는 로컬 작업 (reset, 브랜치 이동, cherry-pick) | 없음. 알림에 "되돌리기"가 있다 |
| 작업 트리의 변경을 버리는 작업 | 선택 창: stash / 버림 / 취소 |
| 원격을 바꾸는 작업 (강제 push, 원격 삭제) | 항상 확인 |

### 3.4 저장소마다 직렬 큐 1 개

같은 저장소의 모든 worktree 가 같은 큐를 쓴다. `index.lock` 과 ref 경합을 막는다.

## 4. 대상 흐름

기준이 되는 흐름: base 브랜치가 다시 쓰였다. 사용자는 자기 브랜치를 새 base 로 옮기고, 자기 커밋을 다시 얹고,
원격을 덮어쓴다.

| 조작 | 미리보기 | 실제 명령 | 확인 |
| --- | --- | --- | --- |
| 커밋 X 에서 "현재 브랜치를 여기로 hard reset" | 브랜치에서 빠지는 커밋 수. 그중 다른 ref 가 닿지 못하는 수 | 백업 ref → `git reset --hard X` | 작업 트리가 깨끗하면 없음 |
| 체크아웃하지 않은 브랜치의 라벨을 X 로 끌기 | 같음 | `git update-ref refs/heads/B X <old>` | 없음. 작업 트리를 건드리지 않는다 |
| 커밋 여러 개 선택 → cherry-pick | 커밋마다: 깨끗함 / 충돌 예상(파일 목록) / 이미 적용됨 | 조상 순서로 정렬 → `git cherry-pick <sha...>` | 없음. 충돌이면 멈춘다 |
| push (로컬과 원격이 갈라짐) | 원격에서 사라지는 커밋 목록. 다른 작성자의 커밋은 경고 | `git fetch origin B` → `git push --force-with-lease=refs/heads/B:<본 sha> origin refs/heads/B:refs/heads/B` | 항상 |

규칙:

- **lease 는 항상 sha 를 명시한다.** 값은 사용자가 확인 창에서 본 원격 sha 이다. sha 가 없는
  `--force-with-lease` 는 백그라운드 fetch 가 추적 ref 를 갱신하면 보호가 없어진다. sha 를 명시하면
  `--force-if-includes` 는 동작하지 않는다 (git 2.50.1 의 `git help push` 로 확인). 그래서 쓰지 않는다.
- **"이미 적용됨"** 은 `git cherry <새 base> <예전 tip>` 의 patch-id 비교로 찾는다. 이 커밋은 기본으로 선택을
  해제한다.
- **충돌 예측** 은 `git merge-tree --write-tree --merge-base=<부모>` 로 작업 트리를 건드리지 않고 계산한다.
  git 2.38 이상이 필요하다. 여러 커밋을 차례로 계산하는 방법은 G3 에서 확인한다.
- **머지 커밋** 의 cherry-pick 은 처음에는 거절한다.
- **다른 worktree 에 체크아웃된 브랜치** 는 `git worktree list --porcelain` 으로 찾는다. 그 worktree 에서
  에이전트 턴이 실행 중이면 거절한다. `akra-agent/slot-*` worktree 는 기본으로 읽기 전용이다.

### 4.1 묶음 작업: "base 다시 맞추기"

- 위의 세 조작을 한 계획으로 묶는다. 엔진은 같다. 묶음은 같은 단계를 큐에 넣는다.
- 감지: 추적 ref 의 reflog 에 forced-update 가 있거나, 브랜치의 커밋 중 base 에 같은 patch 가 있으면 상태 띠에
  알린다.
- 계획 화면: 새 base, 옮길 커밋 목록(선택과 순서 변경), 커밋별 예측, 마지막 단계 "강제 push"(선택).
- 마지막 단계의 대상이 보호 브랜치이면 그 단계를 계획에서 빼고 이유를 보인다.

### 4.2 충돌과 되돌리기

- 충돌은 상태 기계로 다룬다. `CHERRY_PICK_HEAD`, `.git/sequencer`, `MERGE_HEAD`, `rebase-merge/` 를 읽는다.
  동작은 계속, 건너뛰기, 중단, 전체 되돌리기이다.
- 데몬이 죽으면 작업 일지와 위 파일로 다시 이어 간다.
- 되돌리기: 현재 ref 가 작업 후의 sha 와 같을 때만 작업 전의 sha 로 되돌린다.
- 강제 push 의 되돌리기는 백업을 다시 강제 push 하는 새 계획이다. 확인을 받는다.

## 5. Akra 보호 브랜치

### 5.1 정의

- Akra 보호 브랜치는 Akra 가 강제 push 와 원격 삭제를 거절하는 원격 브랜치이다.
- GitHub 의 보호 규칙과 독립이다. Akra 는 GitHub 의 규칙을 조회하지 않는다. 순서는 Akra 목록 검사 → lease 검사
  → GitHub 의 거절이다.
- 로컬 reset 과 로컬 브랜치 이동은 막지 않는다.

### 5.2 규칙

```text
ProtectedBranchRule { id, remote(선택), pattern, source: Automatic | User, enabled, note, created_at }
```

- `pattern` 은 정확한 이름이나 glob 이다 (`release/*`).
- 검사는 push 의 목적지 이름으로 한다. 로컬 이름은 원격 이름과 다를 수 있다.
- 저장 위치는 데몬의 저장소별 store 이다. 같은 저장소의 모든 worktree 가 같은 목록을 쓴다.
- 저장소 안의 파일이나 `git config` 에 두지 않는다. 에이전트가 작업 트리나 `git config` 로 목록을 바꿀 수 있다.

| 층 | 내용 | 변경 |
| --- | --- | --- |
| 자동 | 원격 기본 브랜치 (`origin/HEAD`), Akra 통합 브랜치 | 끄기만 된다. 브랜치 이름을 직접 입력한다 |
| 사용자 | 사용자가 추가한 이름과 패턴 | 추가는 바로 된다. 삭제는 브랜치 이름을 직접 입력한다 |

### 5.3 관리 절차

1. **첫 검토:** 저장소에서 강제 push 를 처음 계획할 때 목록 검토 화면을 1 번 보인다. 검토 전에는 강제 push 를
   실행하지 않는다.
2. **후보 제안:** 열린 PR 의 대상 브랜치, 작성자가 여러 명인 브랜치, `release/*`. 사용자가 고른 것만 넣는다.
3. **변경 경로:** Desktop 의 저장소 설정 화면과 CLI (`akra git protect list | add | remove`) 둘이다.
4. **변경 권한:** 사람이 쓰는 클라이언트의 요청만 받는다. 에이전트 턴과 MCP 경로의 요청은 거절한다.
   kernel 명령의 호출자 값(K4-5)을 쓸 수 있는지는 G4 에서 확인한다.
5. **기록:** 모든 변경을 작업 일지에 쓴다.
6. **1 회 우회 없음:** 강제 push 확인 창에 "이번만 허용"이 없다. 창은 걸린 규칙을 보이고 설정 화면으로 간다.

### 5.4 적용 지점

- domain 의 `ProtectedBranchPolicy` 1 개가 판정한다. 입력은 (원격, 목적지 브랜치, push 종류)이다.
- 계획과 실행 양쪽에서 검사한다.
- 모든 push 경로가 이 정책을 쓴다. `src/adapter/outbound/github/automation.rs` 의 push 경로가 강제 push 를
  하는지는 확인하지 않았다. G4 에서 확인하고 같은 정책에 연결한다.
- 범위 밖: 사용자가 터미널에서 직접 실행하는 `git push -f`. 막으려면 `pre-push` hook 을 설치해야 한다. 이
  계획에 없다.

## 6. 구조

```text
domain       GitOperation, OperationPlan, RefExpectation, OperationStep, ImpactPreview,
             ProtectedBranchRule, ProtectedBranchPolicy, 그래프 행과 레인 배치
application  GitGraphService      행 읽기, 레인 배치, 증분 갱신
             GitOperationService  plan / execute / continue / skip / abort / undo
port         git 저장소 읽기와 쓰기 (outbound) → git CLI adapter
store        작업 일지: op-id, 작업 전 ref, 작업 후 ref, 백업 ref, 상태
inbound      Gateway 메서드와 이벤트. Desktop, TUI, CLI 가 같은 메서드를 쓴다
```

- 의존 방향은 `adapter/inbound -> application -> domain` 이다.
- 레인 배치는 순수 함수이고 domain 에 둔다. git 없이 시험한다.

## 7. 화면 (Desktop)

### 7.1 편의성 기준 (제안값)

- 대상 흐름: 수동은 조작 3 번 + 확인 1 번, "base 다시 맞추기"는 클릭 1 번 + 확인 1 번.
- 모든 동작에 길이 3 개 있다: 오른쪽 클릭, 단축키, 명령 팔레트.
- 백업이 있는 로컬 동작은 창을 띄우지 않는다.
- 조작 뒤 100 ms 안에 화면이 반응한다.

### 7.2 위치와 배치

- 오른쪽 패널이다. "브라우저", "업무" 패널과 같은 자리이다. 최대화할 수 있다.
- 범위는 선택한 스레드를 따른다. 스레드의 작업 디렉터리가 저장소와 현재 브랜치를 정한다.
- 최대화의 3 구역: 왼쪽 ref 목록(로컬, 원격, 태그, worktree, stash, 백업), 가운데 그래프 표, 아래 커밋 상세
  (기존 diff 보기).
- 좁은 패널은 그래프만 보인다. 상세는 서랍이다.
- 맨 위 행은 "커밋하지 않은 변경"이다.

### 7.3 행과 라벨

- 행 높이는 고정이다. 열: 그래프, 라벨, 제목, 작성자, 상대 시간, 짧은 sha.
- 라벨은 모양으로 구분한다. 색만 쓰지 않는다.

| 대상 | 표시 |
| --- | --- |
| 로컬 브랜치 | 채운 칩 |
| 원격 브랜치 | 테두리 칩. 로컬과 같은 커밋이면 칩 1 개로 합친다 |
| HEAD | 굵은 칩과 표식 |
| 보호 브랜치 | 자물쇠 |
| 에이전트 / 스레드 | 배지. 누르면 스레드를 연다 |
| 백업 ref | 점선 칩, 흐린 커밋 |

- 현재 브랜치만 강조색이다. 색은 `design/tokens.css` 의 토큰만 쓴다.

### 7.4 조작

1. **끌기 중에 결과를 말한다.** 놓을 수 있는 대상만 밝힌다. 대상 옆에 결과를 한 줄로 쓴다. 놓을 수 없는 대상은
   이유를 쓴다.
2. **실행 전에 결과를 그래프에 그린다.** 계획 화면이 열리면 예상 결과를 점선 노드로 그린다.
3. **선택 막대.** 커밋을 2 개 이상 고르면 아래에 막대가 나온다: 개수, cherry-pick, revert, 비교.
4. **되돌리기.** 그래프에 포커스가 있으면 되돌리기 단축키가 마지막 git 작업을 되돌린다.
5. **작업 기록 목록.** 작업 일지를 시간순으로 보인다. 줄마다 되돌리기 가능 여부가 있다.
6. **상태 띠.** 그래프 위에 현재 상태를 한 줄로 쓴다: 진행 중인 작업, 충돌, base 다시 쓰임, HEAD 분리.

### 7.5 진행, 충돌, 오류

- cherry-pick 중에는 커밋 행마다 상태를 보인다: 대기, 완료, 충돌, 건너뜀.
- 충돌 파일은 기존 diff 화면으로 연다. 충돌 띠에 "에이전트에 맡기기"가 있다. 사용자가 눌러야 턴이 시작된다.
- 오류는 평문 1 문장, 다음 동작 단추, "원문 보기"이다.

### 7.6 push 단추

- 앞섬과 뒤처짐의 수를 항상 보인다.
- 상태에 따라 이름이 바뀐다: push / 강제 push / pull 필요 / 보호됨.
- 강제 push 확인 창은 사라지는 커밋 목록을 보인다. 다른 작성자의 커밋을 맨 위에 둔다.

### 7.7 찾기와 키보드

- 필터: 브랜치, 작성자, 경로, 메시지. 고정 필터: "내 브랜치", "이 스레드의 브랜치".
- 기본은 강조이다. 일치하지 않는 행을 흐리게 한다. 토글로 숨긴다.
- sha 를 붙여 넣으면 그 커밋으로 간다.
- 명령은 plan 26 H2 의 명령 표에 등록한다.
- 그래프 안의 단일 키와 패널 단축키는 기존 표와 충돌을 확인한 뒤에 정한다.
- 끌기 동작은 모두 키보드 동작이 있다.

### 7.8 체감 속도

- 열자마자 뼈대 행을 그린다.
- 라벨은 바로 옮기고 진행 표시를 붙인다. 실패하면 제자리로 돌린다.
- 갱신 때 스크롤 위치를 sha 기준으로 고정한다.
- 키보드로 빠르게 이동하면 멈춘 행의 상세만 읽는다.

## 8. 성능

목표 (제안값, 측정하지 않았다):

| 항목 | 목표 |
| --- | --- |
| 커밋 10 만 개 저장소의 첫 화면 | 300 ms 이내 |
| 스크롤 | 60 fps |
| ref 변경 뒤 갱신 | 200 ms 이내 |
| 작업 미리보기 | 100 ms 이내 |

방법:

- `git log` 출력을 쪽 단위로 읽는다. 첫 쪽을 바로 보낸다.
- 레인 배치는 위에서 아래로 증분 계산한다. 쪽의 끝에서 레인 상태를 넘겨 다음 쪽이 이어 간다.
- 행은 작게 보낸다. 본문, 파일 목록, diff 는 선택할 때만 읽는다.
- 선택이 바뀌면 이전 읽기를 버린다.
- 작업 뒤에는 전체를 다시 읽지 않는다. `git log <새 tip> --not <이전 tip>` 으로 새 커밋만 읽는다 (G2).
- 자기 작업 중에는 ref 변경 알림을 모으고 끝에 1 번만 갱신한다.
- patch-id 비교는 커밋 200 개까지 바로 계산한다. 넘으면 뒤에서 계산한다.
- `core.fsmonitor` 를 켜지 않는다.
- 메모리 빠른 경로 (G7, 제안): 예측이 모두 깨끗하면 `merge-tree` 와 `commit-tree` 로 커밋을 만들고 ref 를 1 번만
  바꾼다. cherry-pick 의 뜻을 다시 구현하는 위험이 있다.

## 9. 조각

한 조각은 PR 1 개이다. 사용자가 조각마다 시작을 정한다.

| 조각 | 내용 | 상태 |
| --- | --- | --- |
| G1 | 읽기 전용 그래프: 쪽 읽기, 레인 배치, ref 라벨, 가상 목록, 오른쪽 패널 | 이 문서와 같은 PR |
| G2 | 커밋 상세와 diff, 감시와 증분 갱신, 찾기, 에이전트 배지, 백업 ref 표시 | 제안 |
| G3 | 작업 엔진: 계획, 실행, 일지, 되돌리기. 동작은 reset, 브랜치 이동, 체크아웃 | 제안 |
| G4 | cherry-pick: 다중 선택, 예측, 이미 적용됨, 충돌 상태 기계 | 제안 |
| G5 | 보호 브랜치 목록 → fetch 와 강제 push | 제안 |
| G6 | "base 다시 맞추기" 묶음과 끌기 조작 | 제안 |
| G7 | merge, 대화형 rebase, stash, stage | 제안 |
| G8 | 메모리 빠른 경로 | 제안 |

## 10. 시험

- 레인 배치: git 없는 단위 시험.
- git adapter: 임시 저장소 fixture. `src/git_subprocess.rs` 의 시험과 같은 방식이다.
- 작업 엔진의 불변 조건: 모든 작업과 그 되돌리기 뒤에 전체 ref 가 작업 전과 같다.
- 대상 흐름(§4) 전체를 시나리오 시험 1 개로 고정한다.
- Desktop: `npm run check`, `npx vitest run`, 화면 조각은 `npm run e2e` (가짜 Gateway).
- 모델 턴은 필요 없다.
