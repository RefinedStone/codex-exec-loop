02 / ROOT CAUSE

한 칸 움직일 때마다 책 전체를 다시 제본했습니다

스크롤 입력 자체가 느린 것이 아니라, 스크롤 뒤의 렌더링 경로가 대화 길이에 비례해 커졌습니다.

BEFORE · O(history) / frame

매 프레임 전체 투영

  1. 01모든 메시지 재포맷
  2. 02모든 grapheme 재분해
  3. 03전체 soft-wrap 재계산
  4. 04카드 prefix 반복 합산
  5. 05남은 transcript를 새 Paragraph로 복사

짧은 대화에서는 숨겨졌지만, 2,048개 메시지에서 프레임당 약 128ms로 증폭됐습니다.

AFTER · O(viewport) / scroll

단일 문서 + 보이는 구간

  1. 01폭 기반 immutable 문서 1회 생성
  2. 02line-row 시작점과 카드 범위 보존
  3. 03partition_point로 시작 행 탐색
  4. 04보이는 paragraph만 빌려 렌더링
  5. 05key 변경 시 단일 캐시 교체

세션·폭·revision별 캐시를 누적하지 않아 메모리 상한도 명확합니다.

SEMANTIC AUTHORITY ConversationViewModel.messages 정본 대화 상태 · 변경 없음

캐시 무효화 키와 불변 조건 보기

키는 문서 identity/revision, transcript revision, view/debug mode, activity expansion revision, terminal width를 포함합니다. 스크롤 offset은 키가 아니므로 문서를 재생성하지 않습니다.

  • 정본 메시지는 렌더러 캐시가 수정하거나 소유하지 않습니다.
  • 캐시는 정확히 한 문서만 보유하며 이전 revision을 누적하지 않습니다.
  • Unicode grapheme은 포맷된 line에서 빌려 임시 String 할당을 줄였습니다.

03 / TROUBLESHOOTING

증상에서 구조적 원인까지 좁힌 과정

  1. 01

    재현 고정

    :sessions 진입 조건을 2,048 메시지·본문 4줄·120×40 backend로 고정해 “길다”를 측정 가능한 fixture로 바꿨습니다.

  2. 02

    CPU와 메모리 분리 측정

    Cargo 빌드 시간은 제외하고 release 테스트 프로세스만 추적했습니다. wall time은 renderer 내부 Instant, CPU·메모리는 Windows Process에서 수집했습니다.

  3. 03

    프레임별 전체 작업 확인

    입력 이벤트보다 transcript 포맷·wrap·card projection과 임시 할당이 매 scroll draw마다 반복되는 것이 지배 비용임을 확인했습니다.

  4. 04

    표현 계층에만 캐시 배치

    application/domain 정본을 건드리지 않고 ShellRuntime이 단일 presentation document를 소유하도록 경계를 고정했습니다.

  5. 05

    회귀를 실행 가능한 계약으로

    60프레임 프로파일, 600프레임 soak, 캐시 key·단일 entry·viewport 탐색 정적 가드를 함께 추가했습니다.

숫자를 해석할 때의 한계

  • TestBackend 수치는 렌더러 비용을 격리한 것이며, 물리 PTY의 입력→화면 표시 지연은 포함하지 않습니다.

05 / RETROSPECTIVE

이번 수정에서 배운 것

+잘한 점

  • 사용자 체감을 production retention ceiling과 release fixture로 재현했습니다.
  • 성능 때문에 정본 대화 authority를 renderer로 옮기지 않았습니다.
  • 짧은 벤치마크뿐 아니라 600프레임 soak로 캐시 성장 여부까지 확인했습니다.
  • 수치, 원본 로그, 아키텍처 계약을 함께 체크인해 재검증 가능하게 했습니다.

!늦게 발견한 점

  • 기능 테스트는 정답 화면을 확인했지만 프레임 비용의 session-length 민감도를 보지 못했습니다.
  • 순수 함수처럼 보이는 projection 경로가 전체 문서 재작업을 숨기고 있었습니다.
  • 대화가 긴 실제 세션을 여는 수동 시나리오가 성능 gate로 승격되지 않았습니다.
  • 초기 투영과 streaming append 비용은 scroll 비용과 별도 예산으로 관리해야 합니다.
UX

후속 정리: 마우스 캡처를 완전한 제품 불변식으로

Akra의 wheel·card·selection은 앱이 캡처를 소유할 때 한 제품처럼 동작합니다. 공개 :mouse 토글은 상태에 따라 기능이 고장 난 것처럼 보이게 하므로 제거했습니다. 이어서 시작 전 호환 우회도 제거해 fullscreen 진입마다 mouse reporting을 켜고, 종료 복원 과정에서 항상 끄는 단일 lifecycle로 고정했습니다.

06 / NEXT HARDENING

더 보강할 수 있는 지점

“더 빠르게”가 아니라 다음 회귀를 조기에 막는 순서로 우선순위를 정했습니다.

P0

CI 성능 예산

2,048 메시지 scroll p95 ≤ 2ms, rebuild = 1을 gate로 두고 기준 대비 20% 이상 악화 시 실패시킵니다.

P0

Streaming tail 증분 투영

현재 transcript revision 변화는 전체 문서를 재생성합니다. append-only update p95 ≤ 4ms를 목표로 tail block만 갱신합니다.

P1

실제 PTY 지연 매트릭스

Windows Terminal·WSL·tmux·macOS에서 입력→표시 p95 ≤ 16ms와 빠른 drag/copy를 자동 캡처합니다.

P1

개발자 성능 계측

projection hit/miss, build/render ms, visible rows, coalesced pointer sample을 진단 overlay와 JSON artifact로 노출합니다.

P1

Resize burst 안정화

연속 resize 중 폭별 재투영을 합치고, burst 종료 뒤 한 번만 rebuild되는 계약을 추가합니다.

P2

Block/page virtualization

retention ceiling이 2,048을 넘어갈 때를 대비해 문서를 block 단위로 보관하고 메모리 상한을 명시합니다.
