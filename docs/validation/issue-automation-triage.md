# 결정적 이슈 판정 검증 (#2541)

## 실행 경계

수집 worker가 현재 관찰을 저장한 뒤 순수 domain 판정을 실행하고, 별도 판정 레코드를 저장한다. 이 경로는 모델·태스크·실행 허가·외부 쓰기를 만들지 않는다. 기존 TrackedIssue의 수명 상태와 한 단계 CAS 규칙은 유지한다. 목록과 단건 조회는 현재 관찰, 저장된 판정과 낡음 표시를 함께 투영한다.

## 판정 입력과 신뢰

- 선택 조건, 열린 상태, 작성자 또는 현재 선택 라벨을 실제 적용한 행위자의 안정 ID를 검사한다. 로그인 문자열을 신뢰 좌표로 바꾸지 않는다.
- `labels_any`에서는 선택 조건에 맞는 현재 라벨의 최신 적용 이벤트만 신뢰 근거로 인정한다. 다른 라벨의 과거 신뢰 근거로 새 자동화 라벨을 승인하지 않는다. `all_open`에서는 현재 라벨의 검증된 이벤트를 사용할 수 있다.
- 담당자가 한 명이라도 있거나 연결 PR이 확인되면 `already_claimed`이다. 자신이나 신뢰하는 담당자라는 이유로 예외를 추정하지 않는다.
- 메타데이터의 `truncated`, `unavailable`, PR의 `unknown`을 빈 목록이나 연결 없음으로 바꾸지 않는다. 현재 `Unknown` 또는 재관찰 전 legacy 행에는 이전 공유본을 섞지 않는다.
- 공개 정책 판과 자동화 정책 판을 별도로 보존한다. 현재 공유본의 공개 정책 판이 준비 검사의 정책과 맞지 않으면 새 판정을 유효한 것으로 만들지 않는다.

## 준비 검사와 위험

필수 섹션 검사는 기존 `validate_issue`를 재사용한다. `완료 기준`의 비어 있지 않은 Markdown bullet·번호·체크 목록을 읽으며, 코드 울타리·들여쓴 코드·HTML 주석 안의 예시는 기준으로 세지 않는다. 체크 표시는 승인이나 실행 성공을 뜻하지 않는다. plan 24의 acceptance 채널을 문장에서 추정하거나 E1 실행 모델을 만들지 않는다.

제목은 1 KiB, 본문은 64 KiB, 기준은 100개, 기준 하나는 2 KiB까지 허용한다. 한도·지원하지 않는 내용·공개 확인 필요는 준비 상태와 이유에 반영한다. 언급한 저장소 경로는 명시적인 inline code의 상대 경로만 읽으며 URL이나 절대 경로를 저장소 경로로 추정하지 않는다. 확장자 없는 단일 루트 파일명도 보호 패턴과 비교하며, 경로 패턴에 일치하지 않는 일반 단어는 그 자체로 사람 관문을 만들지 않는다. 경로는 최대 128개·개당 1,024바이트, 매칭 glob은 4,096바이트이며 한도를 넘으면 high와 사람 관문을 적용한다. HTML 주석이 섞인 줄은 완료 기준에서 제외하며, 주석 밖에도 내용이 있으면 경로 입력을 불완전한 것으로 표시한다. 순수 주석과 코드 울타리는 경로 예시로 보며, 짝이 맞는 inline code 안의 주석 표기는 문자 그대로 읽는다. 정책의 glob 문법은 `*`, `?`, 독립 segment `**`이며 분류 규칙은 첫 일치가 이긴다. 일치가 없으면 normal, 입력을 확정하지 못하면 high로 처리한다.

관문은 유효 수준과 위험 등급에서 계산하고 사람 필수 조건이 항상 우선한다. high 위험은 모든 관문이 human이다. 사용자 예산 상한 중 하나라도 0이면 budget_exhausted로 사람 확인을 요구하고 자동 시작·마감 후 자동 진행 후보로 세지 않는다. 실제 사용량과 실행 시도의 동적 집계는 후속 예산 경계가 맡는다. spec은 사람 전용이며, E3 증거 게이트가 구현되기 전의 delivery·merge도 human이다. Off/Observe와 아직 연결되지 않은 close는 비활성 관문으로 표시한다. 이 결과는 실행 허가를 대신하지 않는다.

## 저장, 낡음과 관문 판

판정 basis는 안정 이슈 ID, 자동화 정책 판, 공개·준비 정책 판, 원본 필드 해시, 정규화한 메타데이터·준비 조건 지문, 고정 소스 커밋을 구분한다. 본문뿐 아니라 라벨·담당자·PR·신뢰 근거·정책이 바뀌어도 재판정한다. 공유본의 해시를 원본 필드 해시로 대신하지 않는다.

관찰 row revision은 저장 CAS의 기준이고 의미 지문과는 별개다. 저장 시 collection epoch/Observe, 관찰·기존 판정·tracked revision을 다시 확인한다. 완전히 같은 관찰의 재저장은 no-op이며, 의미가 같은 판정은 gate_revision이나 새 issue_triaged 사건을 만들지 않는다. 표시용 login·URL·updated_at만 달라지면 관찰 revision에 맞춰 저장 CAS 연결과 catalog revision만 갱신할 수 있다. 달라진 basis의 관문 판은 1씩 증가하며 overflow를 허용하지 않는다.

조회는 저장된 판정을 새 계산으로 몰래 대체하지 않는다. 현재 입력과 맞지 않으면 stale로 표시하고 wire 관문을 비활성화한다. 다음 worker의 재판정이 성공해야 새 결과가 유효해진다. 깨진 정책은 blocked이며 내장 정책으로 대체하지 않는다.

## 조회와 관찰 보고

`issues`는 기존 안정 ID 순서와 cursor를 유지하고 서버가 정한 그룹을 제공한다. 그룹은 현재 유효 수준과 실제 시작 관문을 사용한다. Off/Observe는 관찰 보고의 가정값이 자동 시작이어도 곧 시작으로 분류하지 않는다. `issue`는 대표 workspace에 결속된 안정 ID를 받으며 unavailable과 not_found를 구분한다. 이유는 닫힌 코드와 `summary`, `next`를 함께 반환한다. Gateway가 없는 command-only 조회도 같은 안정 좌표와 workspace 검증을 거쳐 저장된 단건을 읽는다.

관찰 보고는 한 read transaction의 전체 바인딩을 100행씩 순회해 집계한다. 현재 페이지의 크기로 합계를 바꾸지 않으며 요청 페이지, 단건 결과와 보고는 같은 catalog revision에 결속된다. 전체 본문을 메모리에 모으지 않는다.

보고의 `assumed_mode`는 현재 사용자 자율 상한이고, 각 행의 라벨은 이 가정을 더 낮출 수 있다. 반사실 관찰 결과에는 별도의 `observation_only`, `assumed_mode`, `disposition`이 있으며 실제 gates와 분리된다. 자동 시작, 사람 승인, 마감·중재 대기, 제외, 준비 부족, 불명, 관찰 전용, stale, 미판정, 정책 차단을 구분해 센다. 기존 queued/running/in_review/awaiting_decision/failed는 새 자동 시작으로 세지 않고 done/cancelled는 제외한다.

## 감사와 검증

DB commit 직후 `issue_triaged` 사실을 worker 완료 응답과 별도 mailbox로 전달한다. 수집·판정 사건의 수신 순서를 보존하고 Off·오류·종료 직전에 이미 저장된 사실도 기록한다. 사건에는 안정 좌표와 판 번호만 담고 원문·공유 본문·완료 기준 문장은 넣지 않는다. 강제 프로세스 종료를 가로지르는 durable outbox는 이 경로의 보장에 포함하지 않는다.

검증은 순수 domain 표 기반 회귀, 실제 SQLite의 migration/CAS/stale/no-op/집계, 프로토콜 privacy/scope/그룹·이유, 실제 커널의 수집 → 판정 → 조회 → 본문 변경 → stale → 재판정 시나리오를 포함한다. 커널 회귀는 모델과 외부 공급자를 호출하지 않고 가짜 입력·시계와 격리된 파일을 사용한다. 실행 결과와 남은 한계는 PR 본문·리뷰·CI 댓글에 기록한다.
