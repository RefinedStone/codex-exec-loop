GROK BUILD · XAI-FAST-WORKTREE

Fast Worktree
(CoW / BTRFS)
심층 기술 리포트

Grok Build의 xai-fast-worktree는 git worktree 생성을 파일시스템 CoW·snapshot 문제로 재정의한다. 이 문서는 소스 기준 동작, 전략 우선순위, pool/sync 모델, 그리고 Akra parallel pool과의 경계(채택/비채택)를 고정한다.

파이프라인 보기 ← Grok Build 종합 리포트

One-line thesis

  • 목표: 대형 레포에서도 agent isolation 트리를 빠르게 만들고 재사용
  • 수단: --no-checkout + 병렬 reflink / BTRFS / overlay
  • 운영: pre-created pool + dirty-aware sync
  • Akra: 성능 adapter 후보, delivery 정책 대체 아님 (Eval)

WHY

왜 일반 worktree가 느린가

비용은 “git 등록”이 아니라 “working tree를 채우는 I/O”에 있다.

단계일반 경로비용 특성
등록 git worktree add metadata 저렴
Checkout git가 객체→파일로 워킹트리 채움 파일 수 × 단일 스레드 I/O
Dirty 복제 status + 파일 복사 status가 큰 레포에서 초 단위
삭제 worktree remove / rm -rf 파일 수에 비례
재정의

Fast worktree는 “git가 체크아웃을 잘하게 한다”가 아니라 이미 디스크에 있는 워킹트리(또는 FS snapshot)를 복제해서 checkout 비용을 우회한다.

COPY-ON-WRITE

CoW / reflink 원리

복사 순간에 바이트를 복제하지 않고, 수정 순간에만 블록을 분리한다.

Normal copy

전체 바이트 복사

source/file.rs ──read+write──▶ dest/file.rs 디스크에 내용이 두 번 존재 생성 비용 ≈ 파일 크기
CoW / reflink

블록 공유 복제

source/file.rs ──metadata clone──▶ dest/file.rs 동일 물리 블록 공유 수정 시 해당 블록만 분리 생성 비용 ≈ 메타데이터

구현

copy/cow.rs → reflink_copy::reflink_or_copy(). 지원 FS에서는 reflink, 아니면 일반 copy 폴백. reflink는 기본 umask 권한으로 파일을 만들 수 있어, 직후 set_permissions로 소스 mode(실행 비트 등)를 복원한다.

플랫폼

  • macOS: APFS clonefile / reflink — 실사용 주력 경로
  • Linux: Btrfs/XFS FICLONE; 더 빠른 btrfs subvolume 경로 우선
  • 기타 FS: 일반 copy (기능은 동작, 이득 감소)

PIPELINE

생성 전략 우선순위

CreationMode::Linked|Standalone 실행 시 Linux에서 빠른 경로를 순차 시도한다.

WorktreeBuilder.create() │ ├─ GitCheckout ──────────────────────▶ plain git worktree add (full checkout) │ └─ Linked / Standalone │ ├─ (Linux) try Overlay-on-FUSE ── success ──▶ O(1) return │ ├─ (Linux) try BTRFS snapshot ── success ──▶ O(1) return │ (+ lock/transient git cleanup) │ └─ file-by-file fallback Linked → git worktree --no-checkout + parallel CoW Standalone → .git/ 포함 독립 복제 + CoW / snapshot 폴백 결과 정리
1

Overlay-on-FUSE

특수 워크스페이스 스택. lower 공유 + upper snapshot. 파일 복사 없음.

2

BTRFS subvolume

btrfs subvolume snapshot. 볼륨 단위 CoW. Linux 최적 경로.

3

Parallel CoW

파일 단위 reflink 병렬 복사. macOS 기본 주력. 범용 폴백.

LINKED MODE

Linked worktree + 병렬 CoW 복사

기본 모드. object store는 git linked worktree로 공유하고, 워킹트리 파일만 빠르게 채운다.

①

git worktree add --no-checkout

worktree 메타데이터만 등록. working tree는 비운 채 거의 즉시 완료. git 단일 스레드 checkout을 의도적으로 우회한다.

②

병렬 walk + hash shard workers

ignore::WalkBuilder로 소스 트리 walk. 경로 해시로 worker channel에 분배. worker가 디렉 생성 / 파일 reflink / 심링크 재생성. macOS worker 상한 8 (FD 256 ulimit 대비), 그 외 상한 32.

③

Index / working-tree mode 마무리

PreserveWorkingTree / CleanTracked / CleanAll에 따라 reset·clean 적용. 옵션으로 ignored 파일 추가 복사.

Walk 정책 (함정 방지)

.git은 항상 스킵. global gitignore와 .git/info/exclude는 의도적으로 무시한다. 개인/외부 도구 패턴이 tracked 파일을 조용히 스킵하는 사고를 막기 위함. ignore 크레이트는 tracking 상태를 보지 않는다.

부분 실패 가드

PartialWorktreeGuard가 dest를 감시하다가 성공 전에 drop되면 디렉터리 제거 + linked worktree 등록 정리. 반쯤 만들어진 트리를 다음 요청이 재사용하지 못하게 한다.

BTRFS

BTRFS subvolume snapshot

소스가 btrfs subvolume이면 파일 단위 복사 없이 O(1) 복제한다.

btrfs subvolume snapshot <source> <dest>

결과물

  • 독립 subvolume (파일 트리 즉시 존재)
  • 데이터 블록은 CoW로 소스와 공유
  • 생성 비용 ≈ 메타데이터 (파일 수 비의존)
  • 삭제 시 btrfs subvolume delete도 O(1) 경로

Bind-mount 처리

레포가 /workspace/repo처럼 bind-mount된 경우 snapshot dest는 같은 btrfs FS 안에 만들어야 한다. 실제 snapshot을 mount 내부 경로에 두고, 사용자 dest에는 symlink로 노출한다.

bind mount 대신 symlink를 쓰는 이유: private mount namespace에서도 보이고, 프로세스 재시작 후에도 남는다.

CAP_SYS_ADMIN

BtrfsDelegate — 샌드박스 우회

bwrap 등에서 권한 부족 시 특권 helper에 snapshot/delete/overlay mount를 위임. BtrfsDelegate 트레이트: create_snapshot, delete_snapshot, mount_overlay, unmount_overlay.

Snapshot 직후 필수 cleanup

snapshot은 소스 상태를 원자적으로 통째로 찍는다. 그래서 독성 상태도 같이 온다. cleanup_snapshot_git_state가 즉시 제거: 모든 *.lock (특히 index.lock), MERGE_HEAD/REBASE_HEAD/sequencer//rebase-merge/, linked 등록 worktrees/ 등. 이 단계 없이 git reset조차 실패할 수 있다.

OVERLAY

Overlay-on-FUSE (특수 환경)

repo-fuse 스택: FUSE lower + overlay upper(btrfs)가 감지되면 최우선 O(1) 경로.

new overlay mount lower = existing FUSE lower (공유, 읽기 전용 레이어) upper = btrfs snapshot of current upper work = overlay work dir target = worktree path → 파일 복사 없음 → upper readdir로 pristine 여부 빠르게 판정 후 reset/clean skip 가능
Namespace 제약

overlay mount는 namespace-local이다. private mount namespace에서는 스킵하거나 delegate가 caller namespace 안에 마운트해야 한다. btrfs snapshot+symlink와 달리 “심링크로 노출”이 불가능하다는 점이 핵심 차이다.

일반 macOS 개발 머신 경로가 아니라 SpaceXAI 내부/클라우드 워크스페이스 최적화에 가깝다.

OPTIONS

생성 모드와 working-tree 옵션

CreationMode의미특징
Linked (default) git worktree + object store 공유 가장 흔함, 디스크/시간 효율
Standalone 독립 .git/ 포함 복제 rename 교체 가능, 소스 마커 grok-worktree-source
GitCheckout plain full checkout 단순/안전 폴백, pool bench 경로에도 사용
WorkingTreeMode결과
PreserveWorkingTree 로컬 수정·untracked까지 복제 (기본)
CleanTracked tracked 기준 깨끗 (필요 시 reset --hard)
CleanAll reset + clean -fd 성격 (ignored는 기본 clean 대상 아님)

IgnoredFilesMode

Skip / Copy { skip_patterns } / CopyOnly. build artifact 등 ignored를 워커에 가져갈지 선택. 별도 병렬도 설정 가능.

POOL & SYNC

미리 만들고, 취득 시 최소 갱신

생성 최적화만으로는 부족하다. 운영 모델은 pre-created pool + WorktreeSync다.

[idle pool] worktree A, B, … │ acquire ▼ WorktreeSync 1) HEAD resolve (gix) — 소스 vs worktree 2) 필요 시 git reset --hard <source HEAD> 3) git clean -fd (skip 가능) 4) dirty state 복제 - collect once: git status --porcelain=v2 -z - SourceDirtyState (Bytes, 저렴한 clone) - file reflink/delete + staged add/rm replay │ ▼ agent 사용 │ release ▼ reset/clean → pool 반환 또는 폐기

왜 porcelain v2인가

gix status는 worktree-vs-index 중심이라 staged 칼럼과 worktree 칼럼 (XY) 구분이 부족할 수 있다. 예: "D "(staged 삭제, 파일 잔존) vs " D"(worktree 삭제). sync는 둘을 정확히 재현해야 한다.

status 재사용

큰 레포 status가 ~1.4s 급일 수 있어, 소스 status를 한 번 모아 여러 worktree sync에 공유한다. 리포트에 phase timing(reset_hard_ms, dirty_sync_ms 등)을 남긴다.

설계 포인트

“매번 완벽한 트리를 처음부터 만든다”가 아니라 “거의 맞는 트리를 풀에 두고, acquire 때 HEAD/dirty만 맞춘다”가 완성형이다. pool_perf_bench가 create/warm/sync/release/cleanup 라이프사이클을 측정한다.

TEARDOWN

삭제·orphan GC

1

Overlay 제거

unmount + upper snapshot 삭제 (Linux overlay 경로).

2

BTRFS 삭제

symlink/bind 정리 후 btrfs subvolume delete — O(1). metadata 기반 crash recovery 경로 포함.

3

일반 제거

linked worktree registration 정리 + 디렉터리 삭제. 생성 대비 느린 폴백.

SQLite metadata (feature)

worktree inventory, status, GC, discovery/rebuild. orphan btrfs/overlay snapshot cleanup API 제공. 제품 런타임이 “디스크에 남은 유령 트리”를 회수할 수 있게 한다.

AKRA IMPLICATIONS

Akra에 대한 함의

문제 공간은 겹치고, 성공 기준은 다르다.

축Grok fast-worktreeAkra parallel pool
1차 목표 생성/동기화/삭제 지연 최소화 lease · frozen base · review delivery · cleanup 안전
권위 FS 엔진 + 선택적 inventory DB SQLite planning + application control-plane
성공 정의 깨끗한 트리를 빨리 확보 검수된 범위가 안전하게 통합
격리 단위 worktree (linked/standalone/snapshot) 3-slot pool + branch + frozen OID bounds
EVAL

언제 볼 가치가 있나

  • 대형 monorepo에서 pool create/sync가 operator-visible 병목
  • macOS APFS 또는 Linux btrfs 환경이 명확
  • 정책 코드 변경 없이 outbound git adapter 성능 경로만 교체 가능
REJECT as policy

대체하면 안 되는 것

  • lease serialization / capacity 정책
  • frozen base OID · reviewed-range integration
  • human review default · fail-closed delivery
  • identity-checked cleanup 계약
권장 실험 형태

P2 실험: 실레포에서 (1) 현재 Akra create, (2) --no-checkout+reflink 병렬, (3) 가능하면 btrfs snapshot을 비교. proof target은 latency 샘플 + 환경 스탬프. 이득이 없으면 채택하지 않는다. 라이선스는 Apache-2.0이나 플랫폼 전제·부분실패 정리· sandboxed CAP 이슈를 함께 검토한다.

도입 시 체크리스트

  • macOS 기본: APFS reflink 경로가 실제로 타는지 확인
  • Linux: subvolume 여부, bind-mount, CAP_SYS_ADMIN / helper 필요 여부
  • partial failure reclaim이 Akra cleanup 계약과 충돌하지 않는지
  • policy/application 레이어 무변경, adapter 경계만 수정
  • 벤치 없는 채택 금지
