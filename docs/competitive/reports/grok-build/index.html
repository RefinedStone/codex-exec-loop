COMPETITIVE AUDIT · GROK BUILD OPEN SOURCE

Grok Build는
무엇을 오픈했고,
Akra는 무엇을 가져갈 것인가

2026-07-15 SpaceXAI가 xai-org/grok-build를 Apache-2.0으로 공개했다. 이는 provider-owned full-stack coding agent(TUI + agent runtime + tools + sandbox + MCP/skills/plugins)다. Akra의 방어 축은 여전히 Codex-first 운영·전달 레이어다. 이 보고서는 복제 대상이 아니라 차용할 패턴 / 거절할 범위 / 더 깊게 차별화할 지점을 고정한다.

한 줄 결론: Grok Build의 extension surface와 TUI/pty 검증 밀도는 배우되, harness 소유권·provider 결합·broad tool zoo는 따라가지 않는다.

01

THREAT

완결형 agent 제품

자체 runtime, OS sandbox, MCP/skills/plugins/hooks, subagent, plan mode, ACP, headless, dashboard, CoW worktree까지 한 레포에 있다. “터미널 코딩 에이전트” 카테고리에서 feature breadth 위협이 매우 높다.

02

AKRA EDGE

전달·권위·검수 축

Akra는 SQLite planning authority, 3-slot parallel pool, frozen delivery, human review default, Admin/Telegram 동일 진실 소스를 가진다. Grok Build는 대화형 harness이지 review-delivered control plane이 아니다.

03

ADOPT

패턴만 차용

우선순위: (1) hooks/permission 규칙 모델, (2) plan-mode 승인 UX, (3) agent dashboard / multi-session 가시성, (4) PTY e2e harness 밀도, (5) fast-worktree 아이디어의 선택적 벤치마크. 제품 정체성 확장 금지.

SNAPSHOT

감사 스냅샷

공개 소스 shallow clone과 user-guide/crate 구조를 기준으로 한 정적 감사. 런타임 벤치마크는 포함하지 않는다.

ARCHITECTURE

모듈 경계와 런타임 토폴로지

Grok Build는 monorepo leaf crate 폐쇄로 구성된다. 핵심은 pager(TUI) / shell(agent) / tools / workspace 분리다.

Leader / multi-client

xai-grok-shell::leader는 머신당 단일 leader 프로세스 모델을 구현한다. Unix socket(~/.grok/leader.sock) 위에서 TUI / IDE / headless 클라이언트가 동일 agent 상태를 공유한다. reattach·공유 세션 PTY e2e가 광범위하다.

Tool taxonomy

harness-independent ToolKind / x.ai/tool meta envelope로 codex·opencode·grok_build 구현체를 정규화한다. presentation name, read-only 분류, namespace를 단일 vocabulary로 묶는다. (THIRD-PARTY-NOTICES에 openai/codex, sst/opencode 포트 명시)

Workspace + worktree

xai-fast-worktree: git worktree add --no-checkout + 병렬 CoW 복사, Linux BTRFS/overlay snapshot, SQLite metadata, pool sync API. subagent isolation: worktree와 apply-back 경로와 연결된다.

Persistence surface

~/.grok/ 아래 auth, config, sessions, memory, trusted folders, hooks. 세션 디렉터리에 plan.md, MCP spill, durable log. 외부 OTEL은 double opt-in.

DIFFERENTIATORS

Grok Build의 실질 차별점

마케팅 문구가 아니라 소스·문서에서 확인된 “제품이 다른 이유”.

D1

Provider-owned full harness

모델 API, 인증, 샘플링, compaction, tool runtime, TUI를 한 회사가 소유한다. Akra/Codex 클라이언트 구조와 달리 “protocol client”가 아니라 “agent product”다.

D2

Extension stack 완성도

MCP + Skills + Plugins + Hooks + Personas를 계층으로 분리하고 Claude/Cursor 설정 호환까지 제공한다. 팀/엔터프라이즈 도입 마찰을 줄이는 설계.

D3

Leader multi-client continuity

IDE·TUI·headless가 같은 leader agent에 attach/reattach. 세션 영속과 durable log roundtrip e2e가 존재. “한 작업의 여러 창” 모델을 제품화.

D4

OS-level sandbox profiles

workspace/devbox/read-only/strict + custom extends. deny path를 kernel enforce (Seatbelt / bwrap bind-over). permission rule과 별도 레이어로 방어 심화.

D5

Plan mode as first-class tool loop

enter/exit plan tools + plan.md 단일 편집 허용 + 라인 코멘트 승인 UI. “읽기 전용 탐색 → 인간 승인 → 구현”을 강제하는 워크플로 제품화.

D6

Fast worktree engineering

CoW shard copy, BTRFS snapshot, pool sync, SQLite inventory. subagent isolation과 결합 가능한 저수준 인프라. (Akra parallel pool과 목표 공간은 겹치지만 권위 모델은 다름)

D7

PTY e2e 검증 밀도

pager crate에 wheel flood, paste, resize, welcome braille, folder trust, leader multi-client 등 실제 터미널 시나리오 테스트가 매우 많다. TUI 품질 경쟁력의 핵심 자산.

D8

Background / monitor / loop

장기 프로세스, 주기 프롬프트, 이벤트 스트림 모니터를 agent tool로 내장. “대화 중 서버 띄우고 폴링” 같은 개발 루프를 1st-class로 취급.

ADOPT

Akra가 차용할 만한 좋은 요소

제품 포지션을 강화하는 패턴만. harness 복제는 제외.

ADOPT

1. Plan-mode 승인 UX (라인 코멘트 + approve/request changes)

Grok Build의 plan preview action bar(a/s/c/q)는 Akra planning promote/review surface에 직접 대응 가능하다. 이미 있는 draft→validate→promote 권위에 “사람이 계획을 읽고 라인 단위로 고친 뒤 promote” UX를 얹는 형태가 이상적. 증명 목표: plan preview e2e capture + promote receipt에 comment provenance.

ADOPT

2. Agent dashboard / multi-session board UX

Needs input → Working → Idle 정렬, peek/attach/dispatch, Idle fold, search mode. Akra parallel board + sessions를 통합 운영 보드로 진화시킬 때 정보 설계 참고. 단, 권위는 계속 application control-plane / SQLite. TUI는 projection only.

ADOPT

3. Hooks + permission rule vocabulary (호스트 측 게이트)

PreToolUse blocking, allow/deny glob, dangerous re-prompt 계층은 unattended parallel worker 정책과 잘 맞는다. Akra는 app-server 승인을 대체하지 말고, distributor/planning mutation / git delivery 경계에 호스트 정책 훅으로 도입하는 것이 안전.

ADOPT

4. PTY / real-terminal e2e harness 밀도

wheel flood, paste, resize, reattach, modal focus 등 실패 모드를 테스트 이름에 고정한 방식이 Akra docs/validation 전략과 정합. “한 번 캡처”에서 “재현 가능한 시나리오 스위트”로 확장.

ADOPT

5. Hunk attribution 개념 (agent vs external dirty)

xai-hunk-tracker의 actor 모델은 parallel worker 변경분과 사람/외부 편집을 분리해 delivery bound 검증을 강화할 수 있다. Akra changed-file bounds / cleanliness gate에 attribution 메타를 붙이는 방향.

EVAL

6. Fast worktree (CoW / snapshot) — 벤치 후 결정

대형 모노레포에서 pool create 지연이 병목이면 xai-fast-worktree 아이디어 (no-checkout + parallel CoW + optional BTRFS)를 outbound git adapter 성능 경로로 평가. 정책/lease/delivery 모델은 유지. 라이선스 Apache-2.0이나 의존성·플랫폼 조건 면밀 검토.

EVAL

7. Background monitor / loop 패턴

CI babysit, PR poll, long test 관측은 Akra GitHub review poller / distributor 축과 시너지. 단 “agent tool zoo 확장”이 아니라 application service + TUI projection으로.

EVAL

8. Tool taxonomy meta envelope

progressive activity / review center에 tool kind·read-only·presentation name 정규화는 유용. app-server item types를 대체하지 말고 projection 레이어 vocabulary로만 사용.

REJECT · DIFFERENTIATE

따라가지 말아야 할 것 / 더 깊게 갈 것

Akra 포지션을 흐리는 확장은 거절한다.

REJECT

자체 tool runtime / model harness 소유

Grok Build처럼 in-process tools + sampler + compaction을 재구현하면 Codex protocol-native 이점을 버리고 provider race에 들어간다. app-server를 권위로 유지.

REJECT

Provider breadth / marketplace 제품화

플러그인 마켓·커스텀 모델 라우팅·이미지/비디오 생성은 Akra 핵심 KPI(전달된 PR)와 무관. 필요 시 MCP/skill을 통해 app-server 경로로만.

REJECT

OS sandbox 재구현

Seatbelt/bwrap 프로필 엔진을 Akra가 소유할 이유 없음. sandbox는 app-server 정책 projection + host fail-closed approval로 충분. 중복 구현은 보안 부채.

REJECT

yolo / session-wide remembered grants 기본화

Grok의 bypass/remembered grant는 생산성 좋지만 Akra unattended worker + delivery 모델과 충돌. 현재 “세션 전역 grant 캐시 없음 / fail-closed” 계약을 유지.

DIFF

Review-delivered parallel pool

subagent isolation보다: lease serialization, frozen base OID, human review default, reviewed-range integration, identity-checked cleanup. 여기가 Akra 해자.

DIFF

Planning authority as durable queue

session plan.md가 아니라 SQLite accepted queue + directions + claims. 재시작/distributor recovery/Admin intake가 같은 원장을 본다. 이 축을 더 깊게.

DIFF

Multi-surface operator control plane

Admin game UI, Telegram, planning-tool CLI — 동일 application truth. Grok leader multi-client는 개발자 attach 중심. Akra는 운영자 제어 중심.

DIFF

Inline shell as delivery cockpit

scrollback commit + live viewport는 공유 가능 영역이지만, Akra는 queue/parallel/reviews 명령 체계를 operator cockpit으로 특화. “채팅 품질”이 아니라 “작업 상태 밀도”.
